## マイクを名前で固定する（`audio.device_name`）

オーナー: Bluetooth をつないだり切ったりするとサウンドの設定が変わり、入力が別のマイクに変わることがある。使う
2 つのマイクに固定したい。

- 原因: ロガー・`audio_check`・読み上げ集はマイクを PortAudio の番号（`audio.device_id`）で開く。番号は起動の
  たびに Windows が返す並びで決まり、Bluetooth のつなぎ外しで同じ番号が別のマイクを指す（09-29・30 の記録では
  1 番 = 「Headset (DJI Mic Mini 2-EBA00C」、10-01 は 1 番 = 「Microphone (Wireless Mic Rx)」）。0 番の
  「サウンド マッパー」は Windows の既定に付いていくので、Bluetooth をつないだ瞬間に既定が変わると一緒に変わる。
- 変更: `audio.device_name` に名前（の一部）を優先順に「|」で区切って書くと、起動のたびにその名前のマイクを探して
  開く（`audio/devices.py`）。同じマイクが方式ごと（MME・DirectSound・WASAPI・WDM-KS）に並ぶので、16 kHz で開けて
  番号の若いもの（MME）。どの名前も無ければマイクを開かない（別のマイクで録らない）。MME の名前は 31 文字で切れる
  （「Headset (DJI Mic Mini 2-EBA00C 」）が、`DJI Mic Mini 2` や末尾の `EBA00C` は残るので部分一致で選べる。
- ロガーは 1 本で録る = 名前の順で最初に見つかったマイク。読み上げ集の画面は名前ごとに 1 本ずつ m1・m2 に選ぶ。
- 起動中に Bluetooth をつなぎ外ししたときは、開いているマイクのまま（PortAudio は起動時の一覧しか持たない）。
  名前で選ぶのは起動のたび。
- 確かめたこと: 名前の解釈・優先順・16 kHz で開けるものを先・見つからないときに開かない（`tests/test_audio_devices.py`
  22 件）、`audio_check list` / `level` の表示、起動時の表示、読み上げ集の印。読み上げ集の画面はブラウザで、名前
  2 つ → m1 = Wireless Mic Rx・m2 = DJI、名前なし → 従来どおり番号、名前のマイクが無い → 選ばずに案内、を確認。
- 評価（事前登録）との関係: 変えたのはマイクの選び方と表示だけ。推定器・再生・engine・語の読みは 46a2ba6 のまま
  （事前登録の「コード」の行に書き足した）。

## RDP の音声の出力先（オーナー: 「RDP の時の出力先も設定できる？」）

- RDP の音声の再生先（この端末で再生 / リモート PC で再生 / 再生しない）は接続元の端末（iPhone・iPad・Mac・Windows）の
  設定で、保存した接続ごとに覚える。PC の側（アプリ・config）からは変えられない。Windows には端末へ音を送るのを
  禁止するポリシー（「オーディオとビデオの再生のリダイレクトを許可する」）があるが、禁止しても PC 側で鳴る・PC の
  マイクが見えるようになるとは限らない（試していない）ので勧めない。
- 端末側で再生していると、PC のマイクは WDM-KS 方式にしか見えず開けない（09-30）。名前で固定していても同じ。
  そこで、マイクを開けなかったときに録音できるデバイスが WDM-KS だけなら、ロガーの起動時に「リモートデスクトップの
  音声が接続元の端末に回っているため…」と原因と直し方を出すようにした（`AudioThread.health["rdp_audio"]`、
  `audio_check listen` も）。これまでは「マイク（番号 N）を開けませんでした — Unanticipated host error」だけだった。
- 名前で固定しておくと、端末のマイクを PC に送る設定（録音のリダイレクト）になっていても、名前の違う
  「リモート オーディオ」のマイクで録ることはない。

## カードの登録のスート（オーナー: 「ダイヤとクラブが逆な気がする」）

- `tools/register_cards.py run` は「→ 次: [n/53] Ad（deck 1）— カードをリーダーに置いてください」と表示した札の名前を
  そのまま登録する（表示と登録がずれる経路は無い）。登録の順は ♠A..K → ♥ → ♦ → ♣。

  読み違い。札の強さはスートを入れ替えても変わらないので、これまでの勝者・アクションの記録は変わらない。表示と
  記録の札（ボード・手札）のスートが違う。評価の「ボードの札も合う」は真のアクションのボードを RFID の読みから
  入れ始めるので、直さないままオーナーが本当の札に直すと全ハンドがずれる → 評価の前に直す。
- 確かめ方: `tools/rfid_relay.py watch --seconds 30` を動かし、A♦ と A♣ を 1 枚ずつ席のリーダーに置く（「Ad」「Ac」と
  出るか）。逆なら `tools/register_cards.py swap-suits d c`（バックアップを残して一括で入れ替える。もう一度で元に戻る）。
- 事前登録: このコミットの .py の変更はカードの登録のツールだけ（ロガー・推定器は 4dbb1bc のまま）。
- 結果（オーナー）: A♦ が「Ac」と出た = 逆だった → `swap-suits d c` で直した。10-01 より前の店舗のログの札（ボード・

## 推定の時間の条件をハンドごとに（オーナー: B）

- リハーサルの推定は店舗 PC で 4 ハンド 11 秒（4 プロセス）。40 ハンドのセッションでは「1 セッション 1 分以内」を
  超える見込み → オーナーが B（ハンドごとの条件）を選んだ。
- 開発データ（店舗 25 ハンド、この VM・1 プロセスで順に）: 中央値 2.9 秒・9 割 9.5 秒以内・最長 44.0 秒
  （30.8 秒と 44.0 秒の 2 ハンド）。店舗 PC は約 1.3 倍 → 中央値 4 秒・最長 57 秒ほど。
- 条件: 店舗 PC で 1 ハンドの推定の中央値 15 秒以内・最長 90 秒以内（1 ハンドは 1〜3 分、次のハンドが終わるまでに
  出れば足りる）。`tools/estimate_logs.py --workers 1` が各ハンドの時間とまとめを出す。

## 人が聞けば分かる発話が決まり文句になった（オーナー: 「音量が足りないのでしょうか」）

- 人の耳は小さい音・こもった音でも聞き取れる（画面で音量も上げられる）が、Whisper は小さい・こもった音に
  YouTube の字幕で覚えた決まり文句を出しやすい。18:42 の声は 13:56 の約半分の大きさで、3.4 kHz より上が無い
  （雑音は小さい）。どちらが効いているかは、同じ発話の音量を上げて聞き直すと分かる。
- この VM からは Hugging Face に届かず（403）、Whisper のモデルを取れない → 店舗 PC で
  `tools/audio_check.py gain --session bb4b1b89`（そのままと声の大きさ 3000 にそろえた音を並べる）。
  音量を上げて読めるなら: 入力レベル（Windows の録音レベル・ブースト・マイクを口元へ）か、ロガーで音量を
  そろえてから聞き取る（ロガーの変更 = 評価の版の固定をし直す）。読めないなら: こもった音（Bluetooth の方式・
  付け方・ノイズキャンセル）→ 受信機の経路と比べる。
- 店舗 PC の `audio_check gain --session bb4b1b89`（34 発話）: そのまま 読めた 20・決まり文句 10 → 声の大きさを
  3000 にそろえて 読めた 21・決まり文句 8。音量はほぼ効かない（オーナー: 「あんま変わらんらしい」）。
- 声の部分の周波数の分布（発話の上位 30% のフレーム）: 18:42 は 300〜800 Hz に 81%（13:56 は 77%、09-30 は 77%）、
  800〜1500 Hz 4.2%（6.9% / 7.3%）、2500〜3400 Hz 0.2%（0.4% / 1.5%）、3400〜4000 Hz 0.0%（0.7% / 0.9%）。
  子音の手がかり（2〜4 kHz）がさらに少なく、3.4 kHz でほぼ切れている = こもった音。音量ではなく音の質。
- 次: 同じ配る人で受信機と Bluetooth を `audio_check listen` で比べる。送信機の付け方（服の下・向き・口元からの距離）・
  ノイズキャンセルも確かめる。

- 受信機の `listen` は「設定したマイク（Wireless Mic Rx）が見つかりません」（送信機が Bluetooth 側にいて受信機は

  Whisper だけでは 6/11、第 2 の耳が「コール」「千二百点」「千」を救った。オーナー: 読めなかったのは「スリーウェイ」
  （書き起こしは「シーウェイ」）だけ。18:42 の悪さは付け方か配る人の声の小ささを疑う。
- オーナー: 受信機は運用上使わない（ボタンを押さないとリンクしない）→ Bluetooth の DJI で続け、受信機との比較は
  しない。評価も Bluetooth の DJI で録る（事前登録の「音の設定」）。
- 録音の調べ直し（dB と雑音の床）: Bluetooth の経路は 4 kHz で切れていない。13:55 は声の大きいフレームで 4〜8 kHz が
  雑音より約 40 dB 上、雑音の床は 8 kHz まで平ら = 電話の音質（8 kHz）ではなく 16 kHz の方式で届いている。前の節の
  「3.4 kHz より上がほぼ無い」はエネルギーの割合の話で、dB では全セッション（09-27 の受信機も）7.5 kHz まで入っている

  = 付け方（口元から遠い・服の下・向き）か声の小ささ。09-27 の受信機のセッションは声の大きさは同じくらいで雑音の床が
  20〜25 dB 高く、受信機で決まり文句が多かったのはそのせいの可能性がある。
- 評価の手順 0.（事前登録）に、言った発話の 3 割以上が読めなければ送信機を付け直してもう一度、を足した
  （今日の別の人: 読めないのは 11 のうち 1〜2 = 通る。18:42: 34 のうち 14 = 付け直し）。
- 「シーウェイ」→ スリーウェイ（残りの人数）は評価のあとに足す（語の読みは評価の版で固定）。

## 18:42 のプリフロップが 4 ハンドとも崩れた理由（オーナー: 「ハンドのディールとのタイミングは関係ありませんか？」）

- 配るタイミングではない: 4 ハンドとも、ロガーがハンドを始めた（2 席で手札を読んだ）4〜10 秒あとに最初のプリフロップの
  発話があり、真のアクションのプリフロップ 17 行（4・5・4・4）すべてに、ハンド開始後の書き起こしが 1 つずつある
  （ハンドの外で聞き流した発話は DEBUG なのでログに出ないが、プリフロップの発話は欠けていない）。
- 原因 1（ハンド 2・3・4）: 席の設定の食い違い。ロガーは席 4・5・6・7 で起動、4 人目の手札は毎ハンド席 3 のリーダー
  （Qh 6d / 5h Ad / 6h 5c / 4s Ts）で読まれ、席 7 のリーダーには一度も札が無い。「フォールド」を聞くと手番の順に
  札が席に無い席を探し、一度も札が読めていない席も「無い」に数える（`_absent_seat_for_fold_word`、b6f4f8a から）
  → 各ハンドの最初の「フォールド」が席 7 に付き、席 7 より前の人はコールで補われた（ハンド 3: 席 4 のフォールドが
  「席 4・5・6 コール、席 7 フォールド」）。
- 原因 2（ハンド 1・3・4）: 降りる前の手札がボードのリーダーで読まれ、マックとみた。ハンド 1 席 5 の A♣（配って
  数秒後）・ハンド 3 席 5 の 9♥（レイズの 3 秒後）・ハンド 4 席 4 の 3♦（実際のフォールドの 7.6 秒前）。ハンド 1 は
  BB のフォールドとして 6・7・4 をコールで補ってプリフロップを閉じ、「600」（席 7 のレイズ）がフロップのベットになった。
  一人二役で札を持って中央を通ったのか、席 4・5 の置き方の問題かをオーナーに確認中。
- 原因 3（ハンド 1・2・3）: 聞き違い（「これで終わりです。」= フォールド、「9 百 千」= 900（耳は 九百点・差 -0.7 で
  採らず）、「お疲れ様でした。」= フォールド（耳は コールド → フォールド・差 -4.0 で採らず）、「ご覧いただき
  ありがとうございます。」= フォールド）。額の「センゴヒャク」「ニセンテン」も Whisper は決まり文句にしたが、
  第 2 の耳が 千五百・二千点 と読んで救った。
- 提案（ロガーの変更 = 評価の版の固定し直し、オーナーの返事待ち）: ハンドの始めに、ゲームに入っていない席に
  手札がある・入っている席に札が無いことを警告する / 一度も札が読めていない席には「フォールド」を付けない /
