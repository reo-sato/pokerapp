## 見つけたこと・直したこと

1. **再生の順番**（`integration/replay.py:_in_replay_order`, `integration/engine.py:_handle_seat_signal`）。
   - 再生は `(時刻, camera→rfid→audio)` で並べ替えていた。ボードの札は 2 秒載り続けてから確定し、時刻は最初に
     見えた時刻なので、そのあいだに処理した札の離脱・ストリートの信号より前に流れる（ハンド 2・4・8・9。
     ターンの札が、フロップの信号と席5 の離脱より先に流れた）。
   - live は発話の処理の中で出した信号（札の離脱）を、発話と同じ時刻でその発話の後に記録する。live はその信号を
     アクションを入れる前に反映した（`_apply_observations_before` / 「フォールド」と札の離脱）。
   - 配った直後の「フォールド」でハンドを始め、その処理の中で席6 の離脱を記録していた（ハンド 1）。再生では離脱が
     ハンドの開始より前に届いて捨てられ、フォールドも保留のまま消えていた。
   - → 信号のある記録は記録の順に流し、発話と同じ時刻の信号はそれを出したアクションの直前に置く
     （「オールインフォールド」の離脱は「フォールド」の直前）。時計は巻き戻さない。配布を検出してからハンドを
     始めるまでに届いたそのハンドの信号は、始めてから反映する。信号の無い記録（古い記録・手で書いた fixture）は
     従来どおり時刻順。
   - 最初の直し方（同じ時刻は記録の順）は `tests/test_rfid_folds.py` の再生テストを壊した（同じ時刻の離脱を
     アクションより先に流す必要があった）。発話の処理の中で出した信号 = 「アクションを入れる前に反映した」で、
     両方がそろう。
2. **オールインの言い直し**（`integration/engine.py:_is_restated_allin`, `ALLIN_RESTATE_SEC = 8.0`）。
   - 店舗データの「オーリー」3 回のうち 2 回は、すぐに「オールイン、コール」「オールインフォールド」と言い直していた
     （間 2.1 / 4.2 秒）。fded6f75 でも「オールイン」→ 6.5 秒後に「オールイン、コール、ショーダウン」（まとめの
     言い直し）。店舗の古いコードは「オーリー」を読まなかったので、言い直しの「オールイン」で偶然正しく記録されていた。
     「オーリー」を読むと、言い直しが次の人のオールインになる。
   - → 直前の記録がオールインで、その発話から 8 秒以内に別の発話で「オールイン」なら言い直し（記録しない。
     CLI にお知らせ、元の記録の理由に `allin_restated`）。1 つの発話の中の 2 つ目・あいだにほかのアクションがある
     とき・8 秒より後は 2 人。反例（言い直しでない 2 人の続けてのオールイン）は店舗データに無い。
3. **「2千500」**（`audio/recognizer.py`: `_SEN_DIGITS` / `_MAN_DIGITS` / `_KANJI_DIGITS`、`_AMOUNT_TOKEN`）。
   - 単位のあとの算用数字を足していなかった（2000）。→ 千のあと 3 桁はそのまま、1〜2 桁は百・十の位の省略
     （曖昧）。万のあと 3〜4 桁。漢字の単位のあとの数字（「千500」）も 1 つの額。
4. **回帰テストに書き起こしも**（`tools/eval_store.py:export_fixture` / `check_fixture`）。
   - fixture に `transcripts.jsonl`（読み直しに要る項目だけ）と `reparse_baseline` を書き、いまの読み取りで
     読み直した再生が悪くならないことも確かめる。上の 2 と 3 のような読み取りの変更は、記録の再生
     （記録したときの読み）だけでは見られなかった。
   - 3 セッションを `tests/fixtures/store/2026-09-29-*` に書き出した。上の 1 を外すと d0f055fb が、2 を外すと
     読み直しの d0f055fb ハンド 2・4・8 が失敗することを確かめた。
