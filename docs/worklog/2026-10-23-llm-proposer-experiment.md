# 2026-10-23 LLM の提案を推定器の候補に足す実験（準備）

## 目的

オーナーとの議論（「推定器をクラウドの LLM に任せる設計の是非」）を受けて、**LLM を正本にはせず、候補の提案役に
とどめる案**をオフラインで試す準備をする。10/19 の 8 人卓では推定器の全部正しいハンドが 20/109 で、誤り 87 のうち
73 は正解が候補にそもそも無い（直しの語彙で表せない, 監査 4 回目・改善案）。LLM にハンド全体を読ませ、その解釈を
今の直しの語彙にして候補に足せば、正解が候補に入るか・今の採点で選ばれるかを測れる。

議論で決めたこと（オーナー 10/23）:

- 丸ごと置き換える案（LLM が記録を決める）は採らない。推定器の pokerkit の合法性と採点で検証・選択する。
- 本番の経路・店舗 PC・ADR-0063 D1（推論は店舗 PC）は触らない。効果が数字で出たら ADR-0063 の例外を諮る。
- モデルは **Opus 5.5（上限の確認）と Haiku 5.5（本番の候補）**。安い Gemma 4 31B 級の案も出たが、API の単価は
  Haiku 5.5 とほぼ同じ（入力 $0.10 対 $0.14、出力 $0.50 対 $0.40 / 1M トークン）。Gemma の利点は店内で動かせることだが、
  CPU だけの店舗 PC では 31B は実用的でない見込みで、GPU の PC が要る。まず Opus で上限を測り、Haiku で落ち方を見る。
- API は Max 5x プランの API クレジット（月 $100）で回す。開発データ 174 ハンドの見積もりは Opus 約 $20・Haiku 約 $0.5
  （`--dry-run`、出力 1 ハンド 5,000 トークンと仮定）。

  提案で正解が候補に入る（slow）、偽のクライアントでの呼び出し・キャッシュ・拒否と上限切れ。

## 分かったこと（API を呼ばずに）

- **直しの語彙で真を表せる**: 09/27 027e4b15#1 に真のアクションどおりの解釈を手で入れると、直し 5 つ（読み 2・言われない
  コール 3）で再生が真と一致する（③ なら正しい）。
- **ただし今の採点では負ける**: 言われないコール 3 つ（各 −1.9）と、誤読の「ヘッズアップ」が残ることによる人数の宣言の
  食い違い（−3.0）で、−28.2 対 −23.7（直しなしの再生）。LLM が正しく読めても、選び方は採点（言われないアクションの事前 =
  改善案 (c)）が決める。② と ③ を分けて測るのはこのため。
- 最初の変換は席を足しただけの発話まで直しにしていて（直し 1 つごとに読みの確からしさを払う）、マックの「フォールド」を
  捨てていた。どちらも直した（席は比べない・`muck` の種類を足した）。
