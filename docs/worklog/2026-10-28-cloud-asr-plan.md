オーナー（10/28）:「改善計画として、Whisper による会話の書き起こしを何かの API を利用してクラウド上で行うことを考えたい」
「第 2 の耳の代替は存在しませんか？」→「台帳にトラック H として載せて」。コードは変えていない。

## いまの数字

- 店舗 PC の Whisper（medium・CPU int8）は 1 発話あたり中央値 3.0 秒。10/19 は処理待ちが最大 37 件、聞き取りの遅れは
  中央値 9.3 秒・最大 124 秒（作業ログ `2026-10-19-home-truth.md`・改善案 `2026-10-23-estimator-improvement-plan.md`）。
- 開発データ（`tests/fixtures/store/*/transcripts.jsonl` の `audio_sec`）: プレー 1 時間あたり 500〜900 発話・音声 10〜25 分。
  1〜2 秒の短い発話がほとんど。
- 真のベット / レイズの額を Whisper が読めた 77%・第 2 の耳の上位 3 か文 17%・発話に無い 6%（10/19, 監査 4 回目）。
- ADR-0063 D1: 推論は店舗 PC の CPU で行う。ライブでクラウドを使うならこの決まりを見直す ADR が要る。

## クラウドでやる利点と注意

- 利点: 遅れが無くなる（1 発話 1〜2 秒・並べて投げられる）／大きいモデル（large-v3 級・gpt-4o-transcribe・Chirp 3）／
  店舗 PC が軽くなる（他の店に配るときの条件も下がる）。
- 注意: 卓の会話（発話の半分近くが雑談）を外に送る = お客さんへの掲示と、保存・学習に使わない設定の API ／ ネットが切れたら
  いまの Whisper に戻す二重の作り ／ API の鍵は店舗 PC に置かず、クラウド（ADR-0067 の Cloud Run）を中継に ／
  **1 回ごとの最低課金**（短い発話が多いので、15 秒単位などの課金だと 10 倍以上になる）。

## 第 2 の耳（ReazonSpeech）の扱い

第 2 の耳は書き起こしではなく、決まった候補ごとの log P(候補 | 音声) を出す（候補を当てはめて点を付ける）。推定器と短い語の
分類器はこの点で値を決めている。クラウドの API はこの点を返さない（上位いくつかの文と自信・自分の書いた文字の logprobs・語の
後押し・音声の LLM に選ばせる、はどれも部分的な代わり）。本当の代わりは自分で置くもの:

1. 同じ ReazonSpeech を Cloud Run（CPU）に置く — 点がいまと同じで、分類器・推定器の値を作り直さなくてよい。
2. Whisper large-v3 で候補を当てはめて点を付ける（第 3 の耳）— 精度が上がるかもしれないが、GPU と作り込みが要り、分類器・
   推定器の値は数え直し。

推す形: **第 2 の耳は店舗 PC に残し、クラウドに出すのは Whisper だけ**（重いのは Whisper。第 2 の耳は 1 発話 0.3 秒ほどで
全発話にかけて回っている。ネットが切れても店内で回る）。全部をクラウドに寄せるときは 1。

## H1 の道具（10/28, オーナー「改善案H、whisperのapi利用の実験を行います」）

この環境には音声認識の API の鍵も、音声付きの店舗ログ（開発データに WAV は無い）も無いので、まず比べる道具を作った。
API はまだ 1 度も呼んでいない。

- `tools/cloud_asr.py run <音声付きの zip…> --provider <方式>`: 書き起こしの記録に音声のある発話（声ではない音は既定で
  送らない = ライブも Whisper にかけていない）を API に送り、`<sid>.asr.<方式>.jsonl`（文・秒数・課金の目安）に書く。
  `--dry-run` で件数と課金の目安だけ、`--limit` で試し、途中で止めても続きから（失敗した発話は次に送り直す）。
  方式: `openai-whisper-1` / `openai-4o` / `openai-4o-mini` / `groq-v3` / `groq-turbo` / `deepgram-nova3` / `google-chirp3`。
  OpenAI と Groq にはライブと同じプロンプト（`WHISPER_PROMPT_JA`、`--no-prompt` で外す）・言語 ja。鍵は環境変数
  （`OPENAI_API_KEY` か `POKERAPP_OPENAI_API_KEY` / `GROQ_API_KEY` / `DEEPGRAM_API_KEY` / Google は
  `GOOGLE_CLOUD_PROJECT` と gcloud のトークン）。追加の部品は要らない（標準の urllib）。
- `tools/cloud_asr.py compare <zip…> --results <run の出力>`: 方式ごとに書き起こしの文を置き換え、いまの Whisper と並べる:
  - **アクションの読み**: 配る人が言うアクションのうち発話の読みと合った割合（音声の改善を終える目安と同じ
    `eval_store.listening_stop_metrics` の数え方）と、そのうち**ベット / レイズの額の行**だけの割合
  - **全部正しいハンド**: 置き換えた文をいまの読み取りで読み直して再生した記録の、真のアクションとの一致
  - **第 2 の耳**: 重ねない / 重ねる（ライブと同じ規則）の両方
  - **1 発話の時間**（中央値・最大）と**課金の目安**（料金表は第三者のまとめ = 公式で要確認。Groq は 1 回 10 秒の最低、
    Google Chirp 3 は 15 秒単位として数える）
- 試験 `tests/test_cloud_asr.py`（8 件: 課金の単位・各 API の要求と答えの読み方・鍵が無いとき・送って比べる通し
  （記録の Whisper が聞き違えたレイズを API が正しく聞けば、読みが 1 行・額の行・全部正しいハンドが増える）・失敗した発話・
  `--dry-run` は鍵が要らない・compare のコマンド）。速い組 3548 passed・22 skipped、ruff 問題なし。
- 店舗 PC には入れない（verify-v1 に入れていない）。開発側（このクラウドのセッションか家の PC）で回す。

### 回すのに要るもの（オーナー）

## H1 の結果（10/28, OpenAI の 3 モデル）

入力: 10/26 に作った音声付きの zip の 1〜5（9 分割のうち。6〜9 は未受領）。音声のある発話 1,391（音声 52.6 分）、
セッション a64ec4ad（40 ハンド）・2bbd480e（37 ハンド、音声は 1,191 行のうち 871）・58e694c8（2 ハンド）。真のアクションの
メモは 4 セッションとも空。使った額の目安は合計 $4.75（料金表の目安で数えた）。比べる版はこのブランチ `e527031` +
`--prompt`（下）。全部正しいハンドは「いまの読み取りで読み直して再生」したもの。いまの Whisper = 記録の書き起こし。

第 2 の耳あり（ライブと同じ規則）:

| 方式・プロンプト | アクションの読み | 額の行 | 全部正しいハンド（a64ec4ad） | 1 発話（中央値） |
|---|---|---|---|---|
| いまの Whisper（店舗 PC） | 386/617（63%） | 83/109（76%） | 14/79（14/40） | 約 3 秒（店舗 PC） |
| whisper-1・ライブのプロンプト | 433/617（70%） | 80/109（73%） | 12/79（12/40） | 0.86 秒 |
| gpt-4o-transcribe・ライブのプロンプト | 449/617（73%） | 89/109（82%） | 1/79（1/40） | 0.58 秒 |
| gpt-4o-transcribe・制御の語を抜いた P2 | 449/617（73%） | 84/109（77%） | 4/79（4/40） | 0.60 秒 |
| gpt-4o-mini-transcribe・ライブのプロンプト | 364/617（59%） | 81/109（74%） | 6/79（6/40） | 0.61 秒 |
| プロンプトなし（3 モデル） | 37〜47% | 61〜68% | 3〜5/79 | — |

分かったこと:

1. **プロンプトの語が雑音の上に出る**。ライブの Whisper が雑音に字幕の決まり文句（「ご視聴ありがとうございました」= 捨てられる）を
   返す発話で、gpt-4o-transcribe はプロンプトの語を 1 つ返す（「チェック」「コール」「オールイン」、a64ec4ad で API の方が
   アクションの多い発話 275）。捨てる判定（`is_prompt_echo`）は 1 語では効かない。例文「シート3 レイズ 2千」もかけらで出る
   （gpt-4o 81 回。**ライブの Whisper も「シート3」を出している**: 2bbd480e の書き起こしで 64 行）。
2. **1 つの「ハンド開始」でセッションの残りがずれる**。gpt-4o がライブの「お疲れさまでした」の雑音を「ハンド開始」と書き、
   ハンド 13 で切れて以降のハンド番号がすべて 1 つずれた（1/40 の主因）。「チョップ」（勝者）も雑音・笑い声から 3 回。
   P2（ハンド開始・ウィナー・チョップを抜く）でずれは消えたが、1 語の幻聴（ハンドの先頭の「コール」など）が残り 4/40。
3. プロンプトなしでは語を聞けない（「フォールド」→「Ordu」「これだ」）。語ごとの確からしさ（logprobs）で捨てると、
   雑音の 1 語（文の確率の中央値 0.28）と本物（0.93）は分かれるが、しきい値 0.5 で 10/40 どまり（本物も捨てる）。
   ライブが雑音と判定した発話を捨てて API の文を使う組み合わせも 3/40（gpt-4o）・12/40（whisper-1）。
4. 読めたアクションの数（読みの割合）は gpt-4o が最も多いが、ハンドの正しさは余計なアクションで決まる。

→ OpenAI の 3 モデルは、いまの Whisper の文の置き換えとしてはどれも及ばない（いちばん近いのは whisper-1 の 12/40 対 14/40）。
速さ（0.6〜0.9 秒・並べて投げられる）は利点のまま。次に試すなら: 雑音の発話を API に送らない仕組み（第 2 の耳の短い語の
分類器で「雑談 / 雑音」を先に決める）・Groq の whisper-large-v3（ライブと同じ Whisper 系でプロンプトの扱いが近い）・
ライブのプロンプトから例文「シート3 レイズ 2千」を抜く（ライブにも効くかもしれない = 別の確認が要る）。

道具の変更: `tools/cloud_asr.py run --prompt <文>`（ライブと違うプロンプト）。logprobs の取得と、ハンドごとの比べ方は
実験用のスクリプトで行った（道具には入れていない）。
