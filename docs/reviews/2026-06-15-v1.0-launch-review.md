- **方法**: 4 観点を並列サブエージェント監査（技術完成度・RFID ハード E2E・ビジネス/GTM・運用/セキュリティ/法務）+ テスト/ISSUE/ADR 監査。本書はその統合。

## 0. 結論（エグゼクティブ・サマリ）

1. **コア品質は高い。だが v1.0 を止めるのは「コアロジック」ではなく「運用・統合・配布」の穴。** 会計（ledger/point/settlement）・sync・認証・rules-aware 再構築は実装もテストも厚く（623 passed / 0 skipped、stub/TODO ほぼ無し）、設計トレーサビリティ（ADR 34・ISSUE 19）も優秀。
2. **3 つの独立監査（RFID・ビジネス・技術）が同じ結論に収束した: 「RFID 込み v1.0」が最大リスク。** firmware は別 repo で未実装（L 規模 ×3）、ESP32-S3 1 個で PN5180 ×14（9 席+board 5）は実機 PoC 未済、host にも未修正バグ。**強い推奨 = 音声 v1.0（自店ドッグフード即開始）→ RFID v1.1（段階導入）**。
3. **会計の最終目的が運用上、到達不能。** `close_session` は実装済だが、**どの GUI/CLI/API からも呼べず**、closed session 前提の `commit_settlement`（精算確定）に通常運用で辿り着けない。「1 営業日を締めて精算」が成立しない＝買い手にとって致命。
4. **バックアップが一切ない。** 会計の source of truth は `.gitignore` された単一 JSON（fsync なし・rotation なし）。**自店 LAN でも Crit**（1 回のディスク事故で会計全損）。
5. **ビジネス的には、ハンド記録は #3 の価値。** 市場は薄く（国内 ≈411 店）、店舗が最も金を払うのは ①会計・注文・精算の一元化、②会員アプリ再来店、③自動ハンド記録（差別化フックだが支払い動機は二次的）。→ **ハードは重荷**。これも音声先行を支持。
6. **現状はむしろ「自店単機 v1.0」に対し over-built。** mobile・双方向 sync・L1/L2 認証・player merge・staff write API は **SaaS フェーズの資産**。v1.0（自店）では defer 可能で、その方が出荷が速い。

> **要するに**: コアは良い。v1.0 を「音声 + 会計（締め/精算の導線込み）+ バックアップ + 訂正 UI」に絞れば自店ドッグフードを早期に開始でき、RFID と SaaS 機能は検証データを得てから段階投入するのが最善。

## 3. ビジネス / GTM / 価格（事業監査の要約。ネット使用可・出典は事業監査ログ参照）

- **市場**: 国内アミューズメントポーカー店 ≈ **411 店（2025/1、東京 ≈31%）**、緩やかに純増。**薄い市場** → 特化 SaaS 単体で大型化は困難。SOM は数十〜百数十店規模（金額は要検証）。
- **最も金になる価値の順**: ①会計・注文・精算の一元化（毎日発生・締めミス削減で ROI 明快） ＞ ②会員アプリ再来店（LINE/Google + point、LTV） ＞ ③自動ハンド記録（**差別化フックだが直接の支払い動機は二次的**）。
- **競合・差別化**: 汎用アミューズ POS（EasyPOS/AMUSE 等）は会計/会員は強いが**ポーカー特有（hand 記録・session/seating・point→buy-in 充当・1 方向 ledger）を持たない**。海外ポーカールーム管理/RFID 卓は英語・本場カジノ前提（rake/換金/トーナメント）で**日本アミューズ法に不適合**。堀 = **日本語 × アミューズ特化 × 1 方向会計 × 国産 RFID 統合**。ただし堀は広くない。
- **収益モデル（推奨）**: **ハードはレンタル/リース + 月額 SaaS**。ベースプラン = 会計+注文+会員（間口）、**ハンド記録(音声+RFID)は上位/アドオン**（配信店・本格店向け）。価格レンジ・卓 vs 店課金は要検証。
- **ユニットエコノミクス**: SaaS 部分は高粗利だが、**ハード + サポート工数が薄利/赤字化要因**。1 人で回せる店舗数（オンボーディング・障害対応）が事実上の上限。「ハードが軽い・壊れにくい・遠隔復旧できる」がユニットエコノミクスの生命線。**全数値は実機 BOM（Phase H）+ パイロット実測で要検証**。
- **事業上の v1.0 必須**（技術と別）: 利用規約・プライバシーポリシー・特商法表記、賭博/景表法の運用ガイド、課金/サブスク管理、オンボーディング、障害フォールバックの SLA 化、サポート体制。
- **ドッグフードで検証すべき KPI**: 締め作業時間/現金差異（会計価値）、会員登録率/再来店率/point 利用（集客価値）、自動記録の正答率・障害頻度/復旧時間（ハード成立性）、1 店あたりサポート時間（ユニットエコノミクス）、オンボーディング時間。

## 4. 運用・セキュリティ・法務 リスク登録簿（要点）

| リスク | 種別 | 深刻度 | v1.0 必須緩和 |
|--------|------|--------|---------------|
| read API 無認証（LAN 公開で全会計露出） | 認証/PII | Crit(hosted)/High(LAN) | LAN は 127.0.0.1 厳守。hosted は read 認証化 |
| バックアップ不在 | 整合/可用 | **Crit** | 日次バックアップ+fsync（B2） |
| hosted ephemeral FS 消失（credential/auth_identity は sync 非対象で再構成不可） | 整合/可用 | Crit(hosted) | 外販前: 永続ボリューム/DB（それまで hosted 投入禁止） |
| staff shared token（単一・失効/監査なし） | 認証 | High | ローテーション runbook、hosted は cloud 会計 write 無効化 |
| CORS `*` + レート制限なし | 認証 | High(hosted) | hosted で CORS 限定 + WAF/レート制限 |
| player token secret が空→ephemeral（再起動失効） | 認証/可用 | Med/High(hosted) | hosted は env 固定（env override 未実装→要実装） |
| PIN 4 桁可（防御は LAN+lockout） | 認証 | Med | hosted は 6 桁↑ + レート制限 |
| L2 の利用目的明示・同意・退会削除フロー不在 | PII/法務 | Crit(L2外販) | privacy policy 表示+同意+退会=auth_identity 削除（APPI） |
| unmerge が sync 非伝播（既知） | 整合 | Med | 運用ルール化（確定後 merge、unmerge は単一ノード） |
| 現金突合に弱い（釣り/過払い/返金が汎用 adjustment のみ） | 会計 | Med | 締め差異/返金の記録規約 docs 化 |
| ledger malformed を黙ってスキップ | 整合/会計 | Med | skip 件数の可視警告 + 整合チェック |
| アミューズ線引き（adjustment 負 cash が擬似 payout） | 法務/会計 | Low-Med | 用途制限明文化 + 監査ログ |

**APPI To-Do（外販前）**: 利用規約・プライバシーポリシー（両方不在）、L2 同意/開示/削除フロー、PII 最小化の契約化、安全管理措置（バックアップ=B2 と直結）。
**アミューズ**: point は換金不可（コード上 cash 化経路なし＝担保）+ 運用で現金化禁止を契約化。

## 5. スコープ判断: 「RFID 込み v1.0」 vs 「音声先行」

**監査 3 本（RFID・ビジネス・技術）が独立に「音声先行」を推奨**。根拠:
- RFID は firmware（別 repo L ×3）・ESP32-S3×14ch の実機 PoC・カード 52枚×N デッキの登録ツール（未整備）・host バグ修正が全て未着手 → **v1.0 期日を firmware に人質に取られる**。
- ビジネス上ハンド記録は #3 価値・ハードは最大の重荷 → 先に①会計②会員の価値を自店で実証する方が事業学習が速い。
- アーキ上、confidence 行列・`RFIDEvent`・上流 integration は **hardware 非依存で不変**（契約 §9）。`rfid.enabled=false` で音声単独が成立し、後から RFID を additive 有効化しても上流不変 → **段階導入が技術的にクリーン**。

**推奨**: v1.0 を **「音声 v1.0（自店ドッグフード即開始・出荷可）」** と **「RFID v1.1（後追い）」** に分割。自店ドッグフードは音声で開始し、RFID は **PN5180 ×2-3 slot の最小 PoC**（host バグ #B3・14ch polling 性能・firmware 契約 §2-6 を実証）→ 14ch スケール、と段階化。
**もし「RFID 込み」を v1.0 定義として維持するなら**、firmware 開発状況・別 repo 所在・ハード BOM/予算・期日を**先に確定**する必要がある（＝要確認）。
