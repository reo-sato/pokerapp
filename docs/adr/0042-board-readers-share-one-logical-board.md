# ADR-0042: board reader 全台で 1 つの論理ボードを共有し、位置は検出順で決める

## Status

Accepted

## Date

2026-09-11

## Context

契約 v1.1（ADR-0034 の additive 拡張）は board reader を **ストリート専用**として設計した:
`index`（そのリーダーが受け持つ先頭ボード位置）+ `cards`（そのリーダーに重ねる枚数）を config に
書き、`RFIDEvent.board_index = index + offset`（offset = **その台での**検出順）とした。本番サンプルは

```jsonc
{"reader": 8,  "role": "board", "index": 1, "cards": 3},  // flop 3 枚を 1 台に重ねる
{"reader": 9,  "role": "board", "index": 4},              // turn
{"reader": 10, "role": "board", "index": 5}               // river
```

2026-09-11 の実機確認でこの前提が成立しないことが判明した（ISSUE-0024）。実際の配置は
**ボード領域に board reader が 3 台並んでいるだけ**で、5 枚は左から右へ置かれる。どのカードが
どの台に載るかは置き方次第で、ユーザーの観察では **flop の 2・3 枚目は真ん中の台の方が読みやすい**。
`probe_pcsc watch` でも turn の台に 2 枚目を置いた瞬間に `cards=1 を超える` WARN が出た。

「1 リーダーに複数枚」という**読み取り機構は正しかった**（席 = hole card 2 枚、board = 1 台に
2〜3 枚）。誤っていたのは **位置の決め方を reader 単位に固定したこと**だけである。

`board_index` の消費者は 2 つしかない:

1. `integration/engine.py` の street 自動遷移 — `_board_positions` の**枚数**（3/4/5）で判定。
2. JSON ログの board 配列の並び（PHH は flop 3 枚をまとめて出すので順序を持たない）。

どちらも「ボード全体で何枚目か」で足り、**物理的にどの台が読んだかを知る必要はない**。

## Decision

**board reader 全台を 1 つの論理ボードとして扱い、`board_index`（1..5）は全台を通した検出順
（= ディーラーが配った順）で割り当てる。** config に位置は書かない。

1. **位置の状態は `RFIDThread` に 1 つ**（`_board_index_by_uid: uid → 1..5`）。reader ごとに
   持たない。容量はボードの 5 枚（flop 3 + turn + river）。
2. **割り当て規則**: 新規 UID には空き位置の最小を与える。同じ UID には**覚えていた位置**を
   優先して返す（1 枚だけ浮かせて戻してもボードの並びが変わらない）。5 枚を超えたら WARN +
   `board_index=None`（engine は末尾に追記）。
3. **ボードが 0 枚になったら位置記憶をクリア**する（= ハンドの切れ目。次の flop 1 枚目が
   前ハンドの位置を継がないようにする）。1 枚だけ外している間は他の札が残るので記憶は生きる。
4. **config は `role: "board"` だけ**。旧 `index` / `cards` は **廃止**し、残っていれば起動時に
   WARN して無視する（`probe_pcsc check` の lint でも指摘）。「設定したのに効かない」状態を
   黙って作らない。
5. **board reader は左から右の順に config へ並べて書く**。同じ poll で台をまたいで 2 枚以上
   増えたときの位置順が記載順で決まる（poll ループが config 順に回るため）。
6. lint は「位置の重なり」検査（概念が消えた）を捨て、代わりに **board reader 1 台だけの構成**を
   警告する（5 枚を 1 台に重ねることになり給電不足で読めない可能性が高い、ISSUE-0021 OQ6）。

契約は **`docs/contracts/rfid-usb-ccid.md` v1.3 §4** に反映する。**firmware は無改修**
（firmware は UID を返すだけで役割・位置を知らない = v1.0 からの不変条件）。

## Consequences

### 良くなること

- **物理配置に依存しない**。flop を 3 台に散らしても真ん中の 1 台に 2 枚載せても 1,2,3 になる。
  turn / river がどの台に載っても 4 / 5 になる。台数を変えても config の書き換えは行の増減だけ。
- **設定項目が 2 つ消える**（`index` / `cards`）。「どの台がどのストリート」という運用上の
  取り決めも消えるので、ディーラーは普通に左から置けばよい。
- board reader 5 台（1 台 1 枚）の構成も同じ規則で正しく動く（より一般的なモデル）。

### 代償・制約

- **同じ poll で 2 枚以上増えたとき、1 台に同時に載ったぶんの左右順は保証しない**（UID 順）。
  street 遷移は枚数判定、PHH は flop をまとめて出力なので実害は JSON ログの並びだけ。
  厳密な左右順が必要になったら、台ごとのアンテナ位置とカードの物理位置を対応づける別の機構が
  必要になる（現状は要件にない）。
- **ハンドの切れ目の検出が「ボードが 0 枚」に暗黙依存**する。ハンド終了時にボードを片付ければ
  正しくリセットされる。片付けずに次のハンドを始めると前ハンドの位置が残る（ただし
  `n`（新ハンド）で engine 側の `_board_positions` はクリアされるので、engine の枚数判定は
  正しく 0 から数え直す。RFID 側の位置記憶だけが残る = 次の 1 枚目が 4 などになり得る）。
  → 運用上「ハンドが終わったらボードを下げる」を手順に入れる。将来 engine の新ハンド通知を
  RFIDThread に配れるようにするなら、そこで明示リセットする方が堅い（未実装）。
- 旧 config を使っている環境は WARN が出る（挙動は新モデル）。破壊的だが、この設計は
  **実機に対して誤っていた**ので互換を残す価値がない。

## Alternatives considered

1. **reader ごとの固定 index を残し、`cards` を増やす**（例: 全台 `cards: 5`）。
   位置が台ごとに独立したままなので、真ん中の台に 2 枚載せた瞬間に位置が飛ぶ問題が残る。却下。
2. **物理的な左右位置を config に書き、アンテナ位置から board_index を逆算**。
   1 台に複数枚載った場合の左右は RFID では分からないので実現できない。却下。
3. **board_index を捨てて engine 側で「到着順に末尾追記」に統一**（`board_index=None` 経路）。
   実装は最小だが、1 枚だけ浮かせて戻したときに同じ札が二重に追記され、位置の安定性
   （§8 の「外して戻す」耐性）を失う。却下。
4. **ハンドの切れ目を engine から RFIDThread に通知して明示リセット**。
   より堅いが `IntegrationThread → RFIDThread` の逆方向依存が新たに必要（現状は queue 片方向）。
   「ボードが 0 枚」で実用上足りるので今回は採らない（上の Consequences に残課題として記載）。
