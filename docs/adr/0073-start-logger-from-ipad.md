# ADR-0073: iPad の操作だけでハンドロガーを起動する（店舗サーバーがロガーを起動・停止する）

## Status

Proposed（2026-11-18。オーナー「最終的に、iPad アプリからの操作だけでロガーを起動するようにする。Fable の監査を受けながら」。
草稿を Fable が監査し（下の「監査」）、指摘を反映した改訂版。オーナーの確認待ち）

## Context

いまのセッションの始め方:

1. 店舗 PC に RDP でつなぐ。
2. デスクトップの「ハンドロガー」（`start_logger.cmd` = `main.py --cli --log-file`）を起動する。
   - 真のアクション入力（8791）は、`start_logger.cmd` が別の窓で立てる。
3. ロガーが PC のブラウザで卓の設定画面（`tools/session_setup_ui.py`, `127.0.0.1:8794`）を開く。
   - モード・ブラインド / ストラクチャー・席・名前・持ち点・ボタンを入れて「始める」。
4. 終わりは端末で `q`。
   - 確定していないハンドを閉じて、セッションを閉じる。
   - 聞き流した発話を書き起こす（数分。Ctrl+C で後回し）。

目標は、RDP なしで、iPad の操作だけでこれを全部できるようにすること。

## Decision

### D0. 先にコードなしで確かめる（段階 0）

設計で直せない前提が 2 つある。外れれば A 以降の多くが無駄になるので、最初に店舗 PC で測る。

1. **コンソールのセッションでのマイク**（`tools/audio_check.py listen` をタスクから動かし、ログに出す）。
   - 自動サインインのまま、RDP なしで録音できるか。
   - RDP でつないだ瞬間に、マイクが WDM-KS だけにならないか。これは接続元の音声設定で決まり、PC の側からは変えられない。
   - RDP を × で切断したあと、録音が続くか。
   - 途中で止まったとき、開き直しの作り（`audio/recorder.py`）で戻るか。
2. **タスクと子のプロセスの関係**:
   - 店舗サーバーのタスクを止める・更新が止めるとき、子のプロセスも終わるか、孤児として残るか。
   - 子が残っていると、タスクが「実行中」のままになり、起動し直しが効かなくならないか。

結果で D1 の形（子のプロセスか、別のタスクか）を決める。

結果ごとの手（2026-11-18 に先に用意。手順書 `docs/console-probe.md` の「結果ごとの次の手」）:

| 結果 | 手 |
|---|---|
| RDP の接続・切断で、開いたままのマイクが無音になる（新しく開けば聞こえる） | ロガーがセッションの変化（`core/win_session.py`）を心拍ごとに見て、変わったらマイクを開き直す（`AudioThread.request_reopen`, `audio.reopen_on_session_change` 既定 on）。済み |
| 切断のセッションでは新しく開いても聞こえない | RDP を閉じるときは `rdp_to_console.cmd`（`tscon` でコンソールに戻す, 管理者の確認 1 回）。済み |
| RDP の間だけ聞こえない | プレー中は RDP でつながない。ロガーの状態の `win_session` で iPad のパネルに注意を出す。済み |
| 子のプロセスが残る | D1 のまま（子のプロセス + D7 の引き取り） |
| 子が店舗サーバーと一緒に止まる | D1 を「ロガー専用のタスク」に変える（D1 の最後の段落） |

**段階 0 の結果（2026-11-19, 店舗 PC。`console_probe.cmd` の記録 2 つ）:**

| 状態 | 結果 |
|---|---|
| コンソール（再起動 → 自動サインイン、RDP なし） | 声あり（最大 5387）。**目標の前提は成り立つ** |
| RDP でつないでいる | 声あり |
| × で閉じた（切断） | 声あり（27 回） |
| `rdp_to_console.cmd`（tscon）でコンソールに戻した | 声あり。tscon も動いた |
| 切り替わりの瞬間 | 開いていたマイクが 1 回読めなくなる（`Unanticipated host error`）→ 開き直すと毎回声が戻る（新しく開いても声あり） |
| 店舗サーバーと同じ形のタスクを `schtasks /End` で止めた | **子のプロセスは残った**（本体が止まったあとも動き続けた）。1 つ目の記録で子が一緒に止まったのは PC の再起動 |

決めたこと:

- iPad だけで起動する形は、そのまま進める。
- マイクは、読めなくなったら開き直す（いまの作り）+ セッションの変化で開き直す（2026-11-18 に足した作り）で足りる。
  `rdp_to_console.cmd` は必須ではない（残してよい）。
- D1 は子のプロセスのまま。子が残るので、D7（店舗サーバーが起動し直したら動いているロガーを引き取る・ロガーが動いている
  間は更新を断る）は必須。店舗サーバーが落ちてもロガーは止まらない（利点）。

### D1. 店舗サーバーの見張り役がロガーを起動・停止する（同時に 1 つ）

- iPad の操作で `main.py --headless --setup <file>` を起動し、止める。
- 子は店舗サーバーと同じユーザー・同じセッションで、窓なしで動く。
- 子の環境は明示する:
  - `PYTHONUTF8=1`。
  - 標準出力と標準エラーはログのファイルへ（`pythonw` の子は `sys.stdin`・`sys.stderr` が None）。
  - 鍵などの環境変数は、店舗サーバーが起動したときのもの（`setx` のあとは店舗サーバーの起動し直しが要る。画面に出す）。
- ロガーの優先度は通常にする（推定器の子は低い優先度）。
- 段階 0 の結果、子のままでは寿命を扱いにくければ、ロガー専用のタスク（このユーザー・Interactive）を見張り役が起動する
  形に変える。その場合も、卓の設定は決まった場所のファイル（`logs/logger_setup.json`）で渡し、止め方は同じ `stop`（D6）。

### D2. ロガーを 1 つに限るロックを、すべての起動の入口に（段階 A1）

- `StoreWriterLock` と同じ作り（`core/store_lock.py`）の `logger.lock` を、端末・GUI・`--headless`・`--script` の全部が取る。
- 取れなければ、短く数回やり直してから起動しない（「別のロガーが動いています（PC / iPad）」）。
- 見張り役はロックを**取ってみない**（試し取りの一瞬に起動したロガーが止まるため）。持ち主の情報（pid・起動の入口）と
  状態のファイルの心拍で「動いているか」を判断する。RDP で起動したロガーも iPad から見える。
- ロックの場所は差し替えられるようにする（`run_cli` を呼ぶ試験が並列で走る）。

### D3. 状態とお知らせのファイル（段階 A1）

- `logs/logger_state.json`（数秒ごとに書き直す）:
  - 段階: 起動中 / 卓の設定待ち（端末のロガーはここでセッションがまだ無い）/ モデルの読み込み中 / 動作中 /
    終了中（書き起こし中）/ 終了 / 落ちた。
  - pid、session_id、始めた時刻、版。
  - マイク（開けたか・名前・方式・入力レベル）、RFID（使えるリーダー数・中継）。
  - 書き起こしの方式、モデルを読めなかったときの「音声なしで続行」、聞き取り待ちの件数。
  - 心拍（最後に書いた時刻）。
- `logs/<sid>.notices.jsonl`: 端末の `●` の行・起動時の案内・`[未適用]`・聞き取り・アクション。
  session_id が決まる前のお知らせ（設定待ち・設定の誤り）は `logs/logger_notices.jsonl` に書く。
  - 制御から来た入力には command_id を付ける。iPad は「届いた / 未適用（理由）」を返せる。
- 端末のロガーも同じファイルを書く。RDP で起動した場合も、iPad で状態とお知らせが見える。

### D4. 端末の 1 行を、端末と制御の共通の関数にする（段階 A2）

- 「1 つの操作 → ロガーの中の副作用 + AudioEvent の列」を作る関数を 1 つ作り、端末の入力と制御の両方がそれを通す。
  - 副作用の例: `name`（`players.json` の `find_or_create`・席とお客さんの対応・席を足す）、`rr`（RFID のスレッドに頼む）。
- 制御の翻訳（`core/control_queue.command_to_audio_event`）は純粋なので、副作用はロガーの中の層で実行する。
- **同じ入力から同じ `events.jsonl` になる**ことを試験で守る。
  - いまの `winner` は、端末（席なし）と制御（席つき）で行が違う。揃える。
  - 評価データの再生が変わると推定器の物差しに響く。
- 足す制御:

| 端末 | 制御 | iPad |
|---|---|---|
| `n` / `w` / `r` | `new_hand` / `winner` / `rebuy` | ✅ |
| `cb` / `cs` / `blinds` / `button` / `name <席> -` | `correct_board` / `correct_seat` / `set_blinds` / `set_button` / `sit_out`・`sit_in` | ❌（API のみ） |
| `name <席> <名前>` | `seat_player`（新。名前か player_id） | ❌ |
| `d <席> <金額>` | `reduce_stack`（新） | ❌ |
| `ante on/off/<額>` | `set_ante`（新） | ❌ |
| `clock …` | `clock`（新。いまは同じプロセスの中の関数なので必須） | ❌ |
| `rr` | `reader_restart`（新） | ❌ |
| 打ち込みのアクション・「失礼しました」 | `text`（新。`parse_actions` を通す） | ❌ |
| `q` | `stop`（新。D6） | ❌ |

- 「いま動いているロガー」宛ての受け口 `POST /api/staff/logger/control` を足す（ロックと状態のファイルで宛先を決める）。
  `session_layer` が false で起動したロガー（RDP の起動）にも届く。セッション宛ての今の受け口は残す。
- 動いていなければ 409。読み込み中は受ける（D6 のとおり、新しいセッションの制御は最初から読む）。
- 制御を書く関数は 1 つにし、スタッフの API と真のアクション入力（8791）の両方がそれを通す（8791 はいまファイルに直接書く）。

### D5. `sessions.json` を書く前に読み直す（段階 A2）

- いまのロガーは、起動時に読んだ内容に席の割当を足して、全体を書き直す（読み直さない）。
- そのため、プレー中に iPad で行った変更（公開範囲・別の卓・席の割当）が、次のハンドで消える。
- `SessionRepository` と `PlayerRepository` の書き込みを「ロックのもとで読み直し → 検査し直し → 変更 → 書く」にする。
  - ロックは OS のファイルロックを**別のロックファイル**に掛ける（`sessions.json` は `os.replace` で入れ替わり、Windows では
    開いたままのファイルを置き換えられない）。`atomic_io` に排他は無く、一時ファイルの名前も固定（`<名前>.tmp`）。
  - `players.json` と `sessions.json` はロックを 1 つにする（読み直しが連鎖するので、2 つだと取る順でデッドロックし得る）。
  - 同期の merge（`core/sync.py`）も同じロックを通す。
  - 読み直したあと検査をやり直す（相手が閉じたセッションへの割当は拒む、など）。
  - ハンドの開始で待つのは IntegrationThread。待ちに上限を付け、取れなければ今の動きで書く（警告つき）。
  - 書き込みの失敗を握りつぶさない（いまの `_flush` は `OSError` を捨て、メモリとファイルがずれる）。
- いまある不具合の修正なので、この ADR の他の段階を待たずに単独で先に出せる。

### D6. 段階のある終了（段階 B）

- `stop` を受けたら、端末の `q` と同じ手順を進め、段階ごとに状態のファイルに書く:
  1. 確定していないハンドを閉じて保存する（`_close_open_hand_at_stop`）。
  2. スレッドを止める。
  3. セッションを閉じる。
  4. 「終了（書き起こし中）」: 聞き流した発話の書き起こし。ここから先は止めても記録は壊れない（残りは「ログをまとめる」で
     書き起こせる）。
- 見張り役は、3 までに決めた時間（例 60 秒）で進まなければ止める。止めたあとは後始末をする（D7）。
- `stop` の取りこぼしを防ぐ（いまの取りこぼしは重複排除ではなく、次の 2 つ）:
  - 制御の読み手は、いま起動のあと（モデルの読み込みのあと）に末尾から読み始める。読み込み中に送った制御は読まれない。
    → 新しいセッションの制御のファイルは最初から読む（session_id は毎回新しいので、古い制御は無い）。
  - 制御は 1 件ずつ、先の発話を最大 60 秒待つ。`stop` もその後ろに並ぶ。→ `stop` は発話待ちを通さず先に処理する。
  - 見張り役は、状態が「終了中」に変わらなければ送り直す。
  - 読んだ位置（byte offset）を覚えるのは、同じセッションの再開（段階 E）から。

### D7. 見張り役の引き取りと後始末（段階 C。店に出す前に要る）

- 店舗サーバーが起動したら、ロックと状態のファイルから、動いているロガーを引き取る（pid・session_id）。
  - 前の店舗サーバーが落ちても、ロガーは止めない。
- ロガーが落ちた（ロックが外れ、終了の段階に達していない）ときに**自動でやるのは 2 つだけ**:
  - 状態を「落ちた」にし、お知らせに「ハンド N は記録の途中で止まりました」と出す。
  - `<sid>.live_hand.json` を消す。
- **セッションを閉じるか続けるかは、iPad でスタッフが選ぶ**。閉じたセッションは開き直せない（reopen が無い・閉じた
  セッションへの席の割当は拒む）ので、自動で閉じると段階 E の「同じセッションの続き」ができず、起動し直すと会計が
  2 つのセッションに割れる。選ぶまでは閉じない（お客さんの画面は「進行中」のまま）。
- 確定していないハンドは、`events.jsonl` を手で再生すれば見られる（`tools/eval_store.py --timeline`）。記録の JSON に
  戻す道具は無い（段階 E）。
- 更新（`update.cmd` / インストーラ）は、ロガーが動いている間は断る（または先に `stop` を送る）。

### D8. 見張り役のスタッフの API（スタッフトークン・会計の書き手のプロセスだけ）

- `GET /api/staff/logger`: 状態・session_id・健康・最近のお知らせ。
- `POST /api/staff/logger/start`: 卓の設定の生の入力を受け取る。
  - API でも `build_session_config` を通し、誤りはその場で項目ごとに返す（結果は捨てる）。
  - ロガーに渡すのは生の入力。ロガーが起動のあとにもう一度検証する（時刻準拠の時計がモデルの読み込みの分だけずれない）。
  - `log_dir` などの場所の指定は受け取らない（config の `log_dir`）。
  - 409 = ロックが取られている（PC で起動したロガーを含む）。起動の間隔を制限する。
- `POST /api/staff/logger/stop`: session_id を必ず指定させる（取り違えを防ぐ）。
- `GET /api/staff/logger/notices?since=`。
- 卓の設定の材料: 前回の設定・ストラクチャーの一覧と編集。`session_setup_ui` の中身を API に移し、config の `log_dir` に揃える。
- 8791（真のアクション入力）が認可なしで制御を書ける点: 店舗サーバーの中で動かすのを標準にし、制御を書く受け口はスタッフ
  トークンを求める（画面はログインのときに受け取る）。この PC のブラウザ（127.0.0.1）からは免除する（今の流れを止めない）。

### D9. iPad の画面（段階 A3 と C）

- A3（操作。RDP で起動したロガーにも使える）:
  - D4 の全部の操作。時計。状態とお知らせ。制御が届いたか。
- C（起動と終了）:
  - 「卓を始める」: モード・ブラインド / ストラクチャー・席・名前・持ち点・ボタン。前回の値で開く。
  - 名前は登録済みのお客さんから選べるようにする。設定の形に `player_id` を足す（いまは名前 → `find_or_create`）。
  - 起動中は、段階（モデルの読み込みの秒数）を出す。
  - 「終了」は段階を出す（書き起こし中は「終わってよい」）。

### D10. セッションの持ち主はロガー

- ロガーが起動のときにセッションを作る（いまのまま）。iPad の「卓を始める」= ロガーの起動。
- iPad から起動するときは `session_layer` を使う（宛先を選べるように）。
- スタッフ画面の「セッションを作る」は、ロガーを使わない卓（会計だけ）のために残す。区別のため、セッションにロガーの印
  （例 `source: "logger"`）を足す。凍結した session schema の版上げ（additive）・同期（`core/sync.py`）・クラウドに送る形
  （`core/cloud_payload.py`）まで通す作業になるので、段階 C の見積もりに入れる。

## 段階

| 段階 | 中身 | 店舗の動き |
|---|---|---|
| 0 | 店舗 PC で測る: コンソールのマイク・RDP の接続 / 切断・タスクと子のプロセス（D0） | 変わらない |
| 単独 | `sessions.json` / `players.json` の読み直しとロック（D5。いまある不具合の修正） | プレー中の iPad の変更が消えなくなる |
| A1 | ロック（D2）・状態とお知らせのファイル（D3）・読む API（`GET /api/staff/logger`・notices）・iPad に表示・スタッフ画面のビルド | RDP で起動したロガーの状態とお知らせが iPad に出る |
| A2 | 共通の関数と制御の追加・記録の同一性の試験・いま動いているロガー宛ての受け口（D4） | 変わらない（端末の動きは同じ） |
| B | `--headless`・段階のある終了と `stop`・`text`（D6）・制御を最初から読む・子の環境（D1） | 手で `--headless` を試せる |
| C | 見張り役・引き取りと後始末（D7）・起動と停止の API（D8）・起動と終了の画面（D9 の後半）・更新の検査・セッションの印（D10） | iPad から起動できる（RDP の起動も残す） |
| A3 | iPad の操作の画面（D9 の前半。起動の道筋には要らないので C と並行かあと） | 操作も iPad で全部できる |
| D | 店舗テスト（起動・終了・落ちたとき・RDP をつないだとき）→ iPad の起動を標準に | |
| E | 落ちたあとの「同じセッションの続き」・ログの回収を iPad から・PC の設定画面の整理・「いつも動かしておく」形の再検討 | |

最小の最初の一歩: **段階 0 と A1**（D5 の修正は並行して単独で）。A1 だけで「iPad でロガーの状態とお知らせが見える」が
手に入り、以後の全段階の土台になる。

## Consequences

- Positive:
  - RDP が要らなくなる（設定・起動・操作・終了を iPad で）。
  - 段階 A から、RDP で起動したロガーでも状態・お知らせ・操作が iPad に出る。
  - D5 で、プレー中の iPad の変更がロガーに消される今の問題も直る。
- Negative:
  - 店舗サーバーが別のプロセスの寿命を持つ（引き取り・後始末・更新の検査）。
  - 制御の種類が増える。共通の関数と記録の同一性の試験で、端末との差を作らない。
- Risks（Fable の上位 3 つ）:
  1. コンソールのセッションのマイク。RDP の接続・切断で録音が黙って止まると、記録の正本が欠ける → 段階 0。
  2. 子のプロセスの寿命。更新・再起動・強制終了で、open のまま残るセッション・確定していないハンド・孤児 → D6・D7。
  3. 記録と再生の同一性・`sessions.json` の上書き → D4・D5。

## Alternatives considered

- **ロガーを店舗サーバーの中で動かす**: Why rejected: Whisper の重い処理が API の応答を遅らせる。ロガーが落ちると会計と
  お客さんの画面まで止まる。
- **ロガーをいつも動かしておき、iPad は「始める / 終える」だけ送る**: Why deferred（段階 E で再検討）。
  - 利点: 起動の待ち（モデルの読み込み）が無くなる。プレー中だけ聞く仕組みはすでにある。
  - 障害: 卓の設定がプロセスの起動と結び付いている（`run_cli` の作り）。設定・セッションをプロセスの中で取り替える作りが要る。
- **PC の設定画面を LAN に開く（127.0.0.1 → 0.0.0.0）だけ**: Why rejected: 起動・停止・状態が残る。設定画面に認可が無い。
