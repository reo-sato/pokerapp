# ADR-0073: iPad の操作だけでハンドロガーを起動する（店舗サーバーがロガーを起動・停止する）

## Status

Proposed（2026-11-18。オーナー「最終的に、iPad アプリからの操作だけでロガーを起動するようにする」。Fable の監査を受けて改訂）

## Context

いまのセッションの始め方:

1. 店舗 PC に RDP でつなぐ。
2. デスクトップの「ハンドロガー」（`start_logger.cmd` = `main.py --cli --log-file`）を起動する。
3. ロガーが PC のブラウザで卓の設定画面（`tools/session_setup_ui.py`, `127.0.0.1:8794`）を開く。モード・ブラインド /
   ストラクチャー・席・名前・持ち点・ボタンを入れて「始める」。
4. 終わりは端末で `q`。

iPad でできることは、すでに多い:

- 店舗サーバー（`main.py --serve`, ADR-0065）は、自動サインインのときにタスク `PokerStoreServer`（このユーザー、
  Interactive）で動く。スタッフ用画面 `/staff/`（ADR-0064）・お客さん向け画面・会計・注文・卓モニタ（8790）・
  任意で真のアクション入力（8791）・ハンドごとの推定（ADR-0072）。
- RFID は SYSTEM のタスクの中継（ADR-0070, `127.0.0.1:8792`）から読む。ロガーが RDP の中か外かによらない。
- ロガーが動いていれば、iPad から制御を送れる（`POST /api/staff/sessions/{sid}/control` → `logs/<sid>.control.jsonl` →
  `ControlConsumerThread` → audio_q。ADR-0039）。CLI のロガーはいつも制御を読む。

足りないもの（この ADR で埋める）:

- ロガーを起動・停止する手段が PC の上にしかない。
- 卓の設定画面は PC のブラウザだけ（`127.0.0.1`）。
- ロガーの状態とお知らせ（`●` の行、マイク・RFID・モデルの読み込み）は端末にしか出ない。
- 端末にしか無い操作がある: 下の「操作の対応表」。
- スタッフ画面の「セッションを作る」（`POST /api/staff/sessions`）は、ロガーのセッションとは別物。ロガーは起動のときに
  自分でセッションを作る（`_open_session_layer`）。

## 現状の達成度（2026-11-18）

| 必要なこと | 状態 | いまの実装 |
|---|---|---|
| 店舗 PC の電源を入れるだけで、iPad から使えるサーバーが動く | ✅ | ADR-0065（自動サインイン + タスク） |
| RDP の外で RFID を読む | ✅ | ADR-0070（SYSTEM の中継） |
| iPad の画面の配信・スタッフの認可 | ✅ | ADR-0064・ADR-0021（スタッフトークン） |
| 進行中のロガーへの制御（新ハンド・勝者・リバイ・訂正・ブラインド・席の休み / 参加・ボタン） | ✅ | ADR-0039 + 制御の種類の追加 |
| 真のアクションの入力（iPad / 卓の形） | ✅ | `tools/ground_truth_ui.py`（8791、店舗サーバーの中でも動かせる） |
| ロガーの起動 | ❌ | RDP + `start_logger.cmd` |
| 卓の設定（モード・ストラクチャー・席・名前・持ち点・ボタン・前回の値） | ❌ | PC のブラウザだけ（127.0.0.1:8794） |
| ロガーの状態（読み込み中 / 動作中 / 落ちた）・お知らせ・マイクと RFID の状態 | ❌ | 端末とログファイルだけ |
| 端末にしか無い操作（時計・アンテ・名前・持ち点を減らす・読み取り装置の再起動・打ち込みのアクション・終了） | ❌ | 端末の入力だけ |
| ロガーの終了（確定していないハンドを閉じる・セッションを閉じる・聞き流した発話の書き起こし） | ❌ | 端末の `q` |
| ロガーが落ちたときの扱い | ❌ | 何もしない（RDP で気づいて起動し直す） |
| RDP の外（自動サインインしたコンソール）でマイクを使う | ⚠ 未確認 | いつも RDP の中で起動している |

ざっくり、**土台（サーバー・認可・制御・RFID）は済み、起動・設定・状態・停止の 4 つが無い**。

## Decision

### D1. 店舗サーバーがロガーを子のプロセスとして起動・停止する

- 店舗サーバーに「ロガーの見張り役」を足す。iPad の操作で `main.py --headless --setup <file>` を子のプロセスとして起動し、
  止める。ロガーは同時に 1 つだけ。
- 子のプロセスは店舗サーバーと同じユーザー・同じセッション（自動サインインしたコンソール）で動く。窓は出さない
  （`pythonw`）。
- ロガーを店舗サーバーの中で（スレッドとして）動かす案は採らない（Alternatives）。

### D2. 画面なしのロガー（`--headless`）

- `run_cli` を「組み立て（スレッド・記録・制御）」と「入力の窓口（端末 / 画面なし）」に分ける。組み立ては 1 つにし、
  端末の動きは変えない。
- 画面なしの入口は、卓の設定を JSON のファイルで受け取る。検証は卓の設定画面と同じ `build_session_config`。端末の
  入力・ブラウザは使わない。
- 端末で打てた操作は、すべて制御（D4）で受ける。

### D3. ロガーの状態とお知らせを、ファイルで店舗サーバーに渡す

- ロガーは `logs/logger_state.json` を数秒ごとに書き直す。中身:
  - 段階（起動中 / モデルの読み込み中 / 動作中 / 終了中）、pid、session_id、始めた時刻、版。
  - マイク（開けたか・名前・入力レベル）と RFID（使えるリーダー数・中継）の状態、書き起こしの方式。
  - 最後に書いた時刻（心拍）。
- お知らせ（端末の `●` の行・聞き取り・アクション）は `logs/<sid>.notices.jsonl` に足していく。端末のロガーも同じものを
  書く（RDP で起動した場合も iPad で見られる）。
- 店舗サーバーは、子のプロセスの終了コードと心拍から「落ちた」を判断する。

### D4. 端末だけの操作を、制御の種類に足す（操作の対応表）

| 端末 | 制御 | いま |
|---|---|---|
| `n` / `w` / `r` / `cb` / `cs` / `blinds` / `button` / `name <席> -`（休み） | `new_hand` / `winner` / `rebuy` / `correct_board` / `correct_seat` / `set_blinds` / `set_button` / `sit_out`・`sit_in` | ✅ |
| `name <席> <名前>` | `rename_seat`（新） | ❌ |
| `d <席> <金額>` | `reduce_stack`（新） | ❌ |
| `ante on/off/<額>` | `set_ante`（新） | ❌ |
| `clock …` | `clock`（新。pause / resume / next / prev / set） | ❌（設定画面の中からだけ） |
| `rr` | `reader_restart`（新） | ❌ |
| 読み上げ文（打ち込みのアクション・「失礼しました」） | `text`（新。`parse_actions` を通す = 端末と同じ） | ❌ |
| `q` | `stop`（新。確定していないハンドを閉じて保存・セッションを閉じる・聞き流した発話の書き起こし） | ❌ |

- 新しい制御も、端末と同じ AudioEvent に翻訳して audio_q に積む。記録（events.jsonl）と再生は端末の入力と同じになる。
- `stop` だけは AudioEvent にせず、ロガーの終了の手順（端末の `q` と同じ）を呼ぶ。

### D5. 見張り役のスタッフの API（スタッフトークン・会計の書き手のプロセスだけ）

- `GET /api/staff/logger`: 状態（停止 / 起動中 / 読み込み中 / 動作中 / 終了中 / 落ちた）、session_id、健康、最近のお知らせ。
- `POST /api/staff/logger/start`: 卓の設定を検証して起動する。動いていれば 409。
- `POST /api/staff/logger/stop`: `stop` を送る。決めた時間で終わらなければ止める（記録は直前まで残る）。
- `GET /api/staff/logger/notices?since=`: お知らせ。
- 卓の設定の材料: 前回の設定・ストラクチャーの一覧と編集（いまの `session_setup_ui` の中身を API に移す）。

### D6. iPad の画面（スタッフ用画面）

- 「卓を始める」: モード・ブラインド / ストラクチャー・席・名前（登録済みのお客さんから選ぶ・その場で作る）・持ち点・
  ボタン。前回の値で開く。
- 動作中: マイク・RFID・モデルの状態、お知らせ、よく使う操作（D4）、時計、「終了」、真のアクション入力（卓の形）への導線。
- 店舗サーバーが真のアクション入力（8791）も動かすようにする（`store_server.ground_truth_ui`）。

### D7. セッションの持ち主はロガー

- ロガーが起動のときにセッションを作る（いまのまま）。iPad の「卓を始める」= ロガーの起動。
- スタッフ画面の「セッションを作る」は、ロガーを使わない卓（会計だけ）のために残す。どちらのセッションかは表示で区別する。

### D8. 実施の順番

| 段階 | 中身 | 店舗の動き |
|---|---|---|
| A | `run_cli` を分ける・お知らせと状態のファイル・制御の種類を足す（D2 の前半・D3・D4） | 変わらない（RDP で起動したロガーにも iPad から全操作が届く） |
| B | `--headless` と、ロガーを 1 つに限るロック | 手で `--headless` を試せる |
| C | 見張り役・スタッフの API・iPad の画面（D1・D5・D6） | iPad から起動できる（RDP の起動も残す） |
| D | 店舗テスト: コンソールのマイク・RDP をつないだ / 切ったとき・落ちたとき | 確かめたら iPad の起動を標準に |
| E | 落ちたあとの再開・更新の扱い・PC の設定画面の整理 | |

## Consequences

- Positive:
  - RDP が要らなくなる（設定・起動・操作・終了を iPad で）。
  - 端末にしか無かったお知らせと状態が iPad に出る（段階 A から、RDP で起動したロガーでも）。
- Negative:
  - 店舗サーバーが別のプロセスを起動するので、責任が増える。止め方・落ち方を設計して試す必要がある。
  - 制御の種類が増える。端末と同じ翻訳にして、記録と再生の同一性を試験で守る。
- Risks:
  - コンソールのセッションでマイクが使えるか（D8 の段階 D で確かめる）。
  - RDP でつなぐと、コンソールのセッションが RDP に移る。マイクの行き先が変わることがある（マイクは開き直し続ける
    作りだが、確かめる）。

## Alternatives considered

- **ロガーを店舗サーバーの中で動かす**: Why rejected: Whisper・推定器の重い処理が API の応答を遅らせる。ロガーが
  落ちると会計とお客さんの画面まで止まる。
- **ロガーをいつも動かしておき、iPad は「始める / 終える」だけ送る**: Why rejected（いまは）: マイクと Whisper を
  ずっと持ち続ける。卓の設定がプロセスの起動と結び付いている（`run_cli` の作り）。段階 E で再検討してよい。
- **PC の設定画面を LAN に開く（127.0.0.1 → 0.0.0.0）だけ**: Why rejected: 起動・停止・状態が残る。設定画面に認可が無い。
