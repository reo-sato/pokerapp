# ADR-0063: 製品化の方針 — 他店へ販売する。店舗 PC が正本、クラウドは店外の窓口と店舗の集約

## Status

Accepted（2026-10-11 オーナー決定。方針の記録で、コードは含まない。実装はフェーズ 1〜4 の別タスク）

## Date

2026-10-11

## Context

ここまでの開発は「自店 1 卓 + iPad 1 台 + 店内 LAN」の dogfood を前提にしてきた（`docs/ui-feature-inventory.md`
の前提 1）。推論エンジン（推定器, ADR-0056）と音声入力の精緻化と並行して、**製品として他の店に配る**ための
アプリ化とサーバー側の整備を始める。

現状（verify-v1）:

- 録音・推論・会計・API・お客さん向け画面の配信はすべて店舗 PC（Windows）1 台で完結し、保存は JSON ファイル。
- クラウドは無い。ADR-0029 は「会場が正本 + クラウドはお客さん向けミラー」を Proposed（運用設計のみ）で残している。
- 「店舗」の概念が無い（全データが 1 店のもの）。スタッフは共有トークン 1 個（ADR-0021）。
- お客さんの本人確認は L0 名前選び（既定）/ L1 PIN（実装済・既定オフ）/ L2 LINE・Google（コアのみ, ADR-0031）。

全体設計書（claude.ai の文書「pokerapp 製品化 全体設計書(アプリ・サーバー)」, 2026-10-11）で選択肢を示し、
オーナーが次の 7 点を決めた。

| # | 問い | オーナーの決定 |
|---|------|----------------|
| 1 | 自店専用か、他店にも売るか | **他店にも売るためにアプリ化する** |
| 2 | ホスティング | **推奨（Google Cloud Run + 東京の Postgres）で進める**。詳細の説明は後で |
| 3 | お客さんが店の外から履歴を見られるようにするか | **見られるようにする**（中核機能） |
| 4 | 複数の店に行く人を同じ会員とするか | **同じ人として扱う** |
| 5 | ログイン方式 | **LINE を主に、Google も出す** |
| 6 | ホールカードの公開範囲 | **設定で変えられるようにする** |
| 7 | 利用料の形 | **プレイヤー課金は基本なし。店舗には卓の導入・システム利用料・卓数比例のいずれでも課金できるようにする** |

## Decision

### D1. 店舗 PC が正本、クラウドは店外の窓口と店舗の集約（ADR-0029 D1 を採用して確定）

- 録音・推論エンジン・会計・ハンドの記録は**店舗 PC が正本**。推論は店舗 PC の CPU で行う（GPU 不要の現状を維持）。
- クラウドは店舗 PC から届いた写し（ミラー）で、**お客さんの店外閲覧・サインアップ・注文受付**と**運営（自社）の店舗管理**を担う。
  **クラウドは会計を書かない**（ADR-0029 D6）。
- 同期は**店舗 PC から外向きの HTTPS だけ**（push: 会計・ハンド・registry / pull: 注文・サインアップ）。店のルーターに
  受け口は開けない。マージ規則は `core/sync.py`（ADR-0022/0024/0032）をそのまま使う。
- ネット断・クラウド障害でも店内の録音・会計・注文は止まらない（店内では今どおり店舗 PC に直接つなぐ）。

### D2. ホスティング: Google Cloud Run（東京）+ マネージド Postgres（東京）（ADR-0029 D2 を更新）

- API は既存の FastAPI（`api/server.py`）を**クラウドモード**で 1 コンテナとして Cloud Run `asia-northeast1` に置く。
  画面（`mobile/` の web ビルド）も同じコンテナから配信する（今の `api/static/player/` と同じ方式 = CORS 不要）。
- クラウドの保存は**マネージド Postgres（東京）**。Cloud Run はファイルが消えるため JSON + volume（ADR-0029 D2 の初期案）は
  取らない。repository interface は ADR-0020 で凍結済みなので、保存層の差し替えで UI・契約は変えない。
  事業者（Supabase の東京 / Cloud SQL の東京）はフェーズ 2 の着手時に決める。
- **店舗 PC の保存は JSON のまま**（単独で動く強みを守る）。
- ADR-0029 D2 の「マネージド PaaS（Render / Railway / Fly.io 等）」は本 D2 で置き換える（Render には東京リージョンが無い）。

### D3. 店舗（テナント）の導入

- 新しい概念は**店舗（store）**だけ。クラウドに `stores`（店舗・契約状態・店舗 PC の端末トークン）を持つ。
- **店舗 PC の JSON と契約 schema は変えない**。クラウドが同期を受け取るとき、**認証した端末トークンから店舗 ID を付ける**。
- ID は今のまま（player_id / session_id = UUID、ハンド = `(session_id, hand_id)`, ADR-0004/0006）。全店で重ならない。
- スタッフは**店舗ごとの個人アカウント + 権限（オーナー / スタッフ）**にする。共有トークン（ADR-0021）は店内 LAN の
  互換用として残し、クラウドでは使わない。

### D4. 会員は店舗をまたいで同じ人（ADR-0025 の player_id 不変を維持）

- 会員の本体は **LINE / Google のアカウントにひもづく player_id**（`auth_identity`, ADR-0028/0031）。
- 各店の店舗 PC で名前選びで作られた player は、本人がログインしたときに会員へ**統合**する（ADR-0030 の merge）。
- どの店に来たことがあるかはクラウドの `store_players`（店舗 ID × player_id）で持つ。
- 外部 IdP の sub から player_id を導出しない（ADR-0025 決定 1 のまま）。

### D5. ログインは LINE を主、Google を副、PIN は店内用に残す

- お客さんのクラウドでのログインは LINE（主）と Google（副）。名前選び（L0）はクラウドでは使わない（他人の履歴が見えるため）。
- PIN（L1, ADR-0027）は店内 LAN での本人確認として残す。

### D6. ホールカードの公開範囲は設定で切り替える（ADR-0059 D7 の future scope を前倒し）

- 選択肢は最低限「記録した手札を全員分」と「自分の手札 + ショーダウンで見せた手札だけ」。
- 店舗の既定値 + セッションごとの上書きを持てる形にする（細部はフェーズ 2 の ADR で決める）。
- 公開範囲は read model（`api/read_models.py`）で適用し、店内・クラウドで同じ規則を使う。

### D7. お金の流れ（ADR-0016 / 0035 は不変）

- お客さん → 店の一方向だけ。賞金・換金・ポイントの現金化は**作らない**（ADR-0035）。
- **プレイヤーからの利用料は基本取らない**。
- 店 → 自社の課金は「卓の導入費（機材と設置）」「月額のシステム利用料」「卓数に比例する料金」を組み合わせられるようにする
  （金額と組み合わせは外販の前に決める）。最初は請求書払い、店舗が増えたら継続課金サービス（Stripe など）。

### D8. 開発の順番と、推論・音声の作業との分担

| フェーズ | 中身 | 次へ進む関門 |
|---------|------|--------------|
| 1 店舗内の仕上げ | スタッフ用画面を店舗 PC から配信 / 自動起動 / リリース版での更新 / 同期の常駐 | 自店で 2 週間止まらずに運用 |
| 2 クラウド最小 | Cloud Run + Postgres / 店舗 ID と同期の受け口 / 会計の書き込みを閉じる / 店外での履歴閲覧 | 公開前のセキュリティ確認がすべて済む |
| 3 ログインと会員 | LINE・Google の実連携 / スタッフ個人アカウント / 規約・退会 / 試験店で運用 | 2 店舗目で 1 か月運用 |
| 4 外販の準備 | 運営用画面 / 店舗の登録手順 / 利用料の請求 / 監視と通知 | 外販開始 |

- 製品化の作業が触るのは `api/`・`core/` の保存層（`*_repository.py`・`sync*.py`）・`mobile/`・`staff/`・`installer/`・新設の
  `cloud/`。**推論・音声（`integration/`・`audio/`・推定器まわりの `tools/`）には触れない**。
- 両方が触り得る `api/server.py`・`main.py`・`config_default.json` は小さく変える（クラウドモードは別ファイルに置く、
  設定は項目の追加だけ）。
- 製品化の作業は verify-v1 から切ったブランチで行い、機能 1 つごとに verify-v1 へ合流する。

## Alternatives Considered

- **自店専用で磨き続ける** — 店舗 ID・個人アカウント・クラウドが不要で最も軽い。
  - Why rejected: オーナーの決定は外販（Q1）。
- **クラウドを正本にする（店舗 PC もクラウド API を叩く）** — 店舗間の集約が単純。
  - Why rejected: ネット断で店内の録音・会計が止まる。会計の真実がクラウドの侵害に晒される（ADR-0029 の不採用理由と同じ）。
- **推論をクラウドで行う** — 店舗 PC を軽くできる。
  - Why rejected: オーナーの決定は「端末内で処理」。音声をネットに流す量・遅延・個人情報の面でも不利。
- **Render / Railway / Fly.io（ADR-0029 D2 の候補）** — 運用はさらに手軽。
  - Why rejected: Render に東京リージョンが無い。Cloud Run は東京に置け、使わない時間は課金されない。
- **店ごとに別の会員にする** — 店舗間の個人情報の分離が単純。
  - Why rejected: オーナーの決定（Q4）。通算成績など会員としての価値（ui-feature-inventory A9）が出せない。

## Consequences

- Positive: 店内の運用（オフライン可・会計の真実は店舗）を壊さずに、店外閲覧と複数店舗の運営を足せる。
  既存の API・契約・アプリ・同期のコードをほぼそのまま使える。推論・音声の作業と衝突しにくい。
- Negative / trade-offs: クラウドの運用（秘密の値・CORS・回数制限・監視・DB のバックアップ）、店舗 ID と端末トークン、
  スタッフ個人アカウント、会員の統合フロー、公開範囲の設定が新たに要る。月額のクラウド費用が発生する。
- Neutral / new constraints: クラウドでは名前選び（L0）と共有スタッフトークンを使わない。クラウドの会計 write は常に無効。
