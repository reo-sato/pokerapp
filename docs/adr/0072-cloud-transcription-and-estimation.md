# ADR-0072: 書き起こしと推定器をクラウドで行う（店舗 PC は録音して送る）

## Status

Accepted（2026-11-09。計画を承認。同日、書き起こしの置き場を GPU から API に変えた（追記 1）。テスト中は店舗 PC から API を直接呼び、推定器は店舗 PC でハンドごとに回す形で段階 1 を実装した（追記 2）。クラウドの中継・推定は他の店に配る前に）

ADR-0063 D1（推論は店舗 PC の CPU）・D8（製品化の作業は推論・音声に触れない）と、ADR-0067 D1（送らないもの: 音声・書き起こし・
推定）を、書き起こしと推定について**一部置き換える**。ライブの記録・会計・店内の閲覧が店舗 PC を正本とすることは変えない。

## Date

2026-11-09

## Context

- **書き起こしが店舗 PC の計算に収まらない**
  - 店舗 PC（GEEKOM A8・8 コア）の Whisper medium（CPU・int8）は、1 発話あたり約 3 秒かかる（音声の 1.1〜1.6 倍・8 スレッド）。
    - 10/26 はライブで書き起こし、最大 7 分遅れた（`docs/worklog/2026-10-28-store-1026-audio-review.md`）。
    - 10/28 から書き起こしを後回しにした（`audio.live_transcribe=false`）。そのためライブの記録に声が入らず、**プレー中に
      アクション履歴を見られない**。
  - **書き起こしが溜まると店舗 PC がビジーになり、操作を受け付けないことがある**（オーナー、2026-11-09）。
  - セッション後も、ハンドの間の発話の書き起こしに 38 分かかる（11/05）。
- **取りこぼしの約 8 割は書き起こしで起きている**
  - 言われたのに取りこぼしたアクションの約 8 割は、Whisper が雑談・幻聴・空に書き換えたもの（10/26 のオーナーの聞き取り,
    `docs/estimator-v2/README.md`）。
  - 大きいモデル（large-v3 など）は、店舗 PC の CPU では遅すぎて試せていない。
- **推定器は文字だけで動く**
  - 入力は events・transcripts・offplay・table_state（1 セッション約 20 MB）。音声もモデルも要らない。
  - いまは店舗 PC で動かしておらず、開発側で手で回し、zip で渡している。
- **オーナーの決定（2026-11-09）**
  - 推定した履歴はプレー中（ハンドの数分後）に見せたい。
  - 店の音声をクラウド（東京）へ送ってよい。保存期間を決め、告知を直す。
  - 書き起こしは API で進める（追記 1 の比較を見て, 2026-11-09「進めてください」）。

## Decision

### D1. 計算の置き場

| 処理 | 置き場 | 理由 |
|---|---|---|
| ライブの記録（RFID・engine）・会計・店内の閲覧 | 店舗 PC（今のまま） | ネットが切れても店内を止めない（ADR-0063 D1 の強み） |
| 第 2 の耳（ReazonSpeech） | 店舗 PC（今のまま） | 1 発話 0.24 秒と軽い。ブラインドの宣言をライブで聞き分ける。推定器が使う耳の点数もここで付ける |
| Whisper の書き起こし | **書き起こしの API**（既定は OpenAI の whisper-1。差し替えられる作り。クラウドの中継から呼ぶ） | 発話から 1 秒前後で文字にし、ライブの記録に声を戻す。店舗 PC の重さの原因をなくす。今の Whisper と同じ成績で、GPU の数分の 1 の費用（追記 1） |
| 推定器 | **クラウドの CPU**（Cloud Run） | ハンドの終わりから 2 分以内に推定する。版をクラウドで 1 つにそろえる |

- クラウドにつながっている間、店舗 PC はプレー中に Whisper を回さない。
- つながらない間は、音声を溜めてつながってから送る（D4）。
- API の鍵は店舗 PC に置かない。店舗 PC はクラウド（ADR-0067 の Cloud Run）に音声を送り、クラウドが API を呼ぶ。
- 書き起こしの担当は、方式を設定で差し替えられる作りにする（API の後継のモデル・GPU の自前の Whisper）。卓が増えて
  GPU のほうが安くなったら移れる。
- API に送る音声は国外（米国）で処理される。API 側は学習に使わず、保存は不正利用の監視のための最長 30 日（OpenAI の
  API の既定。要確認）。告知の文面にこれを入れる（D2）。

### D2. 送るものと保存期間

- 送るもの（店舗 PC → クラウド、外向きの HTTPS だけ。店舗の端末トークンで守る）:
  - 発話の音声（`logs/audio/<sid>/*.wav`）
  - events・transcripts（耳の点数）・offplay・table_state・セッションの設定
- 音声の保存期間は **90 日**（オーナーが一任, 2026-11-09）。90 日を過ぎた音声はクラウドから自動で消す。書き起こした文字と推定は、
  記録として残す。
- ディーラー用・プレイヤー用のお願いの紙の録音の一文に、クラウドで書き起こすこと（音声認識の API = 国外で処理）と保存期間を足す。

### D3. 結果の戻し方

- クラウドの閲覧画面は、推定を重ねて出す（`core/hand_estimate.load_record` と同じ重ね方）。
- 店舗 PC は、書き起こしと推定を取りに行く（pull）。
  - `transcripts.jsonl` を埋める。
  - 推定を `<sid>.estimate.shadow.json` に書く。表示に切り替えたら `.estimate.json` に書く。
  - 店内の画面（閲覧・真のアクションの入力・見直し）は、今のまま使える。
- プレー中に見せる順: 本当のアクション（店で入れた分）があればそれ。無ければ推定（要確認の印つき）。どちらも無ければライブ。
  - **オーナーの決定（2026-11-09）: 推定を見せる**（「基本的に推定のほうが成績がいい」）。ADR-0056 の「表示」の合格を待たず、
    要確認の印をつけて見せる（ADR-0056 追記 6 の (a)）。店舗 PC は推定を `.estimate.json` に書く。

### D4. ネットが切れたとき

- 店内の録音・ライブの記録・会計は止めない。
- 音声と行は店舗 PC に溜め、つながったら続きから送る（`cloud_sync_state.json` と同じ方式）。
- プレー中に店舗 PC で書き起こしには戻さない（**オーナー了承 2026-11-09**）。

### D5. 段階

1. **段階 0**: 方式を選ぶ → **whisper-1 に決めた**（追記 1。11/05 と 10/29 の声のハンドで今の Whisper 以上）。
   - 物差し: 読めた割合と、推定器の全部正しいハンド（書き起こしの行の文を置き換えて `tools/bench_hands.py` に通す）。
   - 道具: `tools/cloud_asr.py`（`claude/project-plan-review-byn3lm` の 10/28 の道具。開発のブランチに入れる）。
2. **段階 1**: クラウドで書き起こし → ハンドごとに推定 → 店舗 PC とクラウドの画面に戻す。
   - 先に ADR-0067 の 2e（置き場とセキュリティの確認）を仕上げる。
   - 店舗 PC の送り手（`core/cloud_inference.py`）は店舗サーバーの中に置く。
3. **段階 2**: 仕上げ（落ちたときの扱い・API の失敗と再送・複数の店の上限）。

### D6. 費用の目安（着手前に、公式の価格表とテストの実績で確かめる）

- 1 セッション（2.6 時間・声のある発話 約 1.5 時間）あたり:
  - 書き起こし（API）: 約 100 円以下（whisper-1 は 1 分 0.006 ドル、mini は 0.003 ドル。11/05 のプレー中の 44 分で
    0.34 ドル / 0.17 ドル）
  - 推定器: 約 10〜30 円
- 月 8 セッションで 1,000 円前後。ADR-0067 の予算アラートに、推論の分を足す。
- GPU をセッション中つけておく案（1 セッション 300〜500 円）・店ごとに GPU 付きの PC（1 台 20 万円前後）より安い。

## Consequences

- **良くなること**
  - プレー中にライブの記録へ声が戻る。推定もハンドの数分後に見られる。
  - 店舗 PC が軽くなる。
  - 推定器を直したら、店舗 PC を更新しなくてもクラウドで次のセッションから効く。
  - 開発側と家の見直しが、zip の受け渡しなしでクラウドから取れる。
- **代わりに受け入れること**
  - 書き起こしと推定は、ネットとクラウドに頼る（切れている間は遅れる）。
  - 月 1,000 円前後の費用と、音声を外（API は国外）に出すことの告知・管理。
  - クラウドのサービスが 2 つ増える（書き起こし・推定）。
- **変えないこと**
  - ライブの記録の作り方（engine・RFID）。
  - 会計の書き手が店舗 PC であること（ADR-0065）。
  - 閲覧のクラウドがスタッフ・会計の受け口を持たないこと（ADR-0067 D9）。

## Alternatives considered

- **推定器だけクラウドへ、書き起こしは店舗 PC（後回し）のまま**
  - プレー中に声が入らず、PC の重さも残るので、オーナーの指摘の 2 点が解けない。
- **店ごとに GPU 付きの PC**
  - 初期費用が大きく、店ごとの保守も増える。
- **クラウドの GPU（Cloud Run の L4）で自前の Whisper**（最初の案）
  - 1 卓の発話はまばらで GPU が 9 割以上遊ぶ。1 セッション 300〜500 円と API の 5〜8 倍。Cloud Run の L4 は東京に無いようで、
    近くてもシンガポール。精度を上げる大きいモデルを使えるのが利点だが、いまは測っていない。卓が増えたら比べ直す。
- **medium をクラウドの CPU で**
  - GPU と同程度の費用で遅く、精度の改善もない。
- **gpt-4o-transcribe**
  - 読めた割合は高いが、雑音に「ハンド開始」などを書いてハンドの区切りがずれ、推定器の成績が落ちる（追記 1: 20〜39/72 対 45/72）。
- **LLM で推定**
  - 10/23〜24 に試して効果が無く、打ち切った（`docs/worklog/2026-10-23-llm-proposer-experiment.md`）。

## 追記 1（2026-11-09）: OpenAI の API での比べ直しと、書き起こしの置き場の変更

オーナーの問い「GPU の書き起こしは OpenAI の API より結構高くなる？」→ 費用を比べ直した（GPU は API の 5〜8 倍）。
10/28 の API の比較（10/19・10/26 の音声 = ヘッドセットの前・雑音もほとんど捨てていない）を、11/05 の音声で行い直した
（プレー中の声のある発話 1,290 件・44 分。書き起こしの行の文だけ置き換えて推定器に通した）。

| 書き起こし | アクションの読み | 推定器の全部正しいハンド | 1 発話 |
|---|---|---|---|
| 今の Whisper medium（店舗 PC） | 90% | 45/72 | 約 3 秒 |
| whisper-1 | 90% | 45/72（+4 / −4） | 1.1 秒 |
| gpt-4o-mini-transcribe | 82% | 45/72（+5 / −5） | 0.6 秒 |
| gpt-4o-transcribe（制御の語を抜いたプロンプト） | 88% | 39/72 | 0.8 秒 |
| gpt-4o-transcribe（今のプロンプト） | 90% | 20/76 | 0.7 秒 |

whisper-1 と mini は今の Whisper と同じ成績で、速く安い。精度は上がらないが、この ADR の目的（プレー中に声を戻し、
店舗 PC を軽くする）には足りる。→ 書き起こしの置き場を API に変えた（D1）。

10/29（声の録れていた 36 ハンド、プレー中の 558 発話・15 分）でも比べた:

| 書き起こし | 声のハンドの全部正しい | 良くなった / 悪くなった |
|---|---|---|
| 今の Whisper medium | 14/36 | — |
| whisper-1 | **17/36** | 3 / 0 |
| gpt-4o-mini-transcribe | 14/36 | 4 / 4 |

2 日の合計で whisper-1 62・今の Whisper 59・mini 59。要確認の付かない誤りはどれも 0。→ **既定は whisper-1**。mini は
費用が半分なので、whisper-1 が使えなくなったときの代わりの候補。詳細は作業ログ。

## 追記 2（2026-11-09）: テスト中の形 — 店舗 PC から API を直接呼び、推定器も店舗 PC で

オーナーの答え（2026-11-09, 段階 1 の計画を承認）:
- **whisper-1 は、テスト中は店舗 PC から直接呼ぶ。** 鍵は店舗 PC の環境変数（`POKERAPP_OPENAI_API_KEY`、`setx` で 1 回）。
  リポジトリ・`config.json`・ログには置かない。他の店に配る前に、クラウドの中継へ切り替える（D1 の「鍵は店舗 PC に置かない」は
  そのときに満たす）。
- **推定器は店舗 PC でハンドごとに回す。** Whisper を止めれば CPU が空く（1 ハンド 中央値 数秒）。クラウドに音声・記録の受け口、
  推定の担当、戻す仕組みを作らずに済む。推定は今の同期（`core/cloud_sync.collect` → `load_record` の重ね合わせ）でクラウドの
  画面にも届く。

実装（段階 1 のテスト中の形）:

| 部品 | 中身 |
|---|---|
| `core/remote_asr.py` | `OpenAITranscriber`（`WhisperTranscriber` と同じ約束）。声かどうか（Silero VAD）は店舗 PC で判定し、声でなければ呼ばない。失敗は `RemoteAsrError` |
| `audio/recorder.py` | `audio.transcriber=openai` のとき、その場で書き起こしてロガーに使う（`live_transcribe` を true 扱い）。失敗した発話は音声を保存して後回しの列へ。つながらない間は呼ばない（5 → 60 秒で試し直す）。その間もブラインドの宣言は第 2 の耳で。書き起こしの行に `asr`（`openai-whisper-1`） |
| `main.py` | 鍵が無ければ知らせて店舗 PC の Whisper に戻す。音声の保存とセッション後の送り直しの印を必ず付ける |
| `core/live_estimator.py` | 店舗サーバーの中の見回り（5 秒ごと）。ハンド N を次のハンドが始まったら（無ければ確定から 60 秒で）推す。窓の中の入力の目印（書き起こしの行・events の数・窓が閉じたか）が変わったら推し直す（1 ハンド 3 回まで）。推定は子プロセス `tools/estimate_logs.py --hands N --write` を低い優先度で 1 本ずつ |
| `core/truth_hand.truth_view` | `viewer_api.show_truth`（お客さんには真のアクションだけ）のときも、真のアクションが無いハンドは推定を見せる（D3 の順: 真のアクション → 推定。ライブの記録だけのハンドは今までどおり見せない） |
| `core/audio_retention.py` | 店舗 PC の発話の音声（`logs/audio/<sid>/`）を `audio.keep_days`（既定 90）日で消す（店舗サーバーが 1 日 1 回） |

- お客さんの画面は要確認の印を出さない（ADR-0044 の移植でお客さんには隠した）。推定のハンドかどうかの表示も今は無い。
  要るかは店舗テストのあとでオーナーに確かめる。
- 確かめたこと: ハンドごとに推した結果は、セッションのあとで推した結果と同じ（`tests/test_live_estimator.py`、11/05 の
  ログをハンドごとに足しながら回した確認は作業ログ）。
