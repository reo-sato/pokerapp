## 0. 何を確かめるか

10/19 の 8 人卓で、推定器の全部正しいハンドは 20/109。誤り 87 のうち 73 は**正解が候補に無い**（直しの語彙で
表せない）。LLM にハンド全体（発話 + RFID の時刻表）を読ませ、その解釈を今の直しの語彙（read / insert / button）に
直して候補に足すと、

1. 正解が候補に入るハンドが増えるか（**found**）
2. 今の推定器の採点でそれが選ばれるか（**全部正しい**）
3. 悪くなるハンド（今の推定器では正しいのに誤る）が出ないか

を測る。本番の経路・店舗 PC・推定器の値（`PARAMS`）は変えない。LLM は正本にしない。

## 1. 比べる条件（同じハンド・同じ実行）

| 条件 | 中身 |
|---|---|
| ① 今の推定器 | 直しの組を持ち込まない（`HandWindow.seeds` = 空） |
| ② 提案つき | LLM の解釈ごとの直しの組を候補に足し、今の推定器の採点で選ぶ |
| ③ LLM が選ぶ | LLM の 1 番目の解釈を今の再生にかけた記録（合法性だけ engine が確かめる） |
| ④ LLM 単独 | LLM の答えた `actions` をそのまま記録とみなす（ボードは RFID） |

モデル: **Claude Opus 5.5**（`claude-opus-5-5`, 上限の確認）と **Claude Haiku 5.5**（`claude-haiku-5-5`, 本番の候補）。
思考は adaptive・effort `high`。Opus はサーバー側のフォールバック（`fallbacks: "default"`）あり、Haiku には無い。

## 4. 判定（評価 = 10/19）

- **採る方向**（ADR-0063 の例外をオーナーに諮る）: ② が ① より全部正しいハンドで **+15 以上**（20 → 35 以上）、かつ
  found が増え、かつ開発 B で「要確認なしで悪くなった 0・悪くなった 40 ハンドで 1 以下」（推定器の事前登録 §4 と同じ）。
- **打ち切る**: Opus で ② も ③ も ① から **+5 未満**。小さいモデルでも届かないとみなす。
- **別の議論にする**: ③（LLM が選ぶ）だけが大きく良い = 採点がボトルネック。LLM に選ばせるのは正本に近づくので、
  オーナーの判断が要る。
- Haiku 5.5 が Opus 5.5 の改善の半分以上を保てば、本番の候補として費用を見積もる。

報告は Wilson の 95% 区間つき。良くなった / 悪くなったハンドの名前を全部出す。

## 5. 送るもの・費用

- 送る: 席番号・ボタン・ブラインド・持ち点・手札とボードの札（RFID）・札の離脱の時刻・書き起こしの文と第 2 の耳の候補。
- 送らない: 名前・真のアクション・メモ・音声。10/19 は送る前にオーナーの了承を取る。
- 費用: 実行前に `python tools/llm_candidates.py --dry-run` で見積もる（開発データ 174 ハンドで Opus 約 $20・Haiku 約 $0.5 の
  目安）。パイロット 10 ハンドの `usage` で置き換える。Max プランの API クレジット（月 $100）の範囲で回す。
