## 3. トラック同士のぶつかり

### 3-1. 日程が実態と合っていない（D）

`docs/estimator.md` の手順は「10/17 まで音声の改善 → 10/20〜10/24 に 5〜6 人卓 2 セッションで準備の確認（誤り 6 以下・
要確認なしの誤り 0）→ 届かなければ 11 月初めまでにオーナーが選ぶ」。しかし:

- 10/20〜10/24 の 5〜6 人卓のセッションの記録（作業ログ・開発データ）がまだ無い。
- 10/19 の 8 人卓では推定器の全部正しいハンドが 20/109（verify-v1 の版で 24/107）、要確認は 109/109。監査 4 回目は
  「この種の卓では誤り 6 以下に届かない」と書いている。
- B（v2）に進むなら推定器は作り直しになり、11 月初めまでに固定できる版は無い。

→ 11 月初めの判断の中身（(a) 合格の条件を変える / (b) 推定器を要確認の候補を出す道具にとどめる / (c) v2 ができるまで
判断を延ばす）を、B の段取りと一緒に決める必要がある。

### 3-2. C の比べる相手（今の推定器）が古い版

- このブランチ（`claude/project-plan-review-byn3lm`）は verify-v1 より 14 コミット遅れている。C の「① 今の推定器」は
  推定器の内容の指紋 `fbf568d7a6af`（10/23 3 の版）。verify-v1 にはそのあと推定器にも効く直しが 3 回入っている
  （10/23 4〜6: 声の遅れで付け直す・額の丸めと数え上げ・読めない席はフォールド）。
- 採点も変わっている（verify-v1 の `dd07272`: オールインは種類だけで比べる）。
- C は開発データ（10/14 まで・4 席まで）を使うので 10/19 向けの直しの影響は小さいとみられるが、0 ではない。
- → C の報告には比べた推定器の内容の指紋を必ず書く。C の結論を出す前に verify-v1 をこのブランチに取り込み、① と ② を
  測り直す（③ LLM が選ぶ・④ LLM 単独は推定器の版に依らない）。**取り込みは C の採点が終わってから**（途中で入れると
  数字の出どころが混ざる）。

### 3-3. C の「② 提案つき」の結果は v1 の採点に縛られる

C の準備でも分かっているとおり、LLM が正しい解釈を出しても、選ぶのは v1 の採点（027e4b15#1 は −28.2 対 −23.7 で負ける）。
B が採点を作り直すと ② の結論は変わりうる。

- C から残る結論は「**LLM の提案で正解が候補に入る割合**」（採点に依らない）と「③ LLM が選ぶ」「④ LLM 単独」。
- 「② 提案つき」は v1 の採点の性質を測るものとして読む。B の ① ができたら、同じ提案を v2 の採点で選び直す。

### 3-4. A が推定器の基準を動かし続ける

A のライブの規則は世界の再生にも効くので、直すたびに推定器の内容の指紋と物差し（開発データ 140/174・10/19 の数）が動く。
B・C は測るときの基準の版（内容の指紋・値の指紋・コミット）を記録し、比べるときは同じ版どうしで比べる。

### 3-5. B と C とこのセッションが同じブランチ

B・C・この台帳のセッションが `claude/project-plan-review-byn3lm` を使っている。push の前に必ず `git pull` する。
B が実装に入るときは、C の道具（`integration/estimator.py` の `HandWindow.seeds`）と同じファイルを触るので、
どちらかの作業が終わってから始めるか、B 用に別のブランチを切る。

## 4. 進める順（推す案）

1. A の計画を承認する（ほかのトラックと独立。今日のうちに店舗 PC に入れられる）。
2. C の採点（実行中）の報告を待つ。報告には推定器の内容の指紋を書いてもらう。
3. B は ① 任意の列の採点（= オラクルの採点）だけを作る。v1 の採点と v2 の採点の両方で「真の列の点 > 1 番の点」を出す。
4. C の終了後に verify-v1 をこのブランチへ取り込み、C の ①② を測り直す。
5. 3 と 4 の結果を並べて、v2 に進むか（② 以降）・LLM を候補の提案役に使うか・11 月初めの判断をどうするかをオーナーが決める。
