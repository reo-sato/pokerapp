## 3. トラック同士のぶつかり

### 3-1. 日程が実態と合っていない（D）

`docs/estimator.md` の手順は「10/17 まで音声の改善 → 10/20〜10/24 に 5〜6 人卓 2 セッションで準備の確認（誤り 6 以下・
要確認なしの誤り 0）→ 届かなければ 11 月初めまでにオーナーが選ぶ」。しかし:

- 10/20〜10/24 の 5〜6 人卓のセッションの記録（作業ログ・開発データ）がまだ無い。
- 10/19 の 8 人卓では推定器の全部正しいハンドが 20/109（verify-v1 の版で 24/107）、要確認は 109/109。監査 4 回目は
  「この種の卓では誤り 6 以下に届かない」と書いている。
- B（v2）に進むなら推定器は作り直しになり、11 月初めまでに固定できる版は無い。

→ 11 月初めの判断の中身（(a) 合格の条件を変える / (b) 推定器を要確認の候補を出す道具にとどめる / (c) v2 ができるまで
判断を延ばす）を、B の段取りと一緒に決める必要がある。

### 3-2.（解消）C の比べる相手が古い版だった・C の結果が v1 の採点に縛られる

C の打ち切りで解消。打ち切りの判断は版の差（内容の指紋 `508cac7e08b8` と verify-v1 の差）では変わらない大きさ
（② 提案つき −1・③ LLM が選ぶ −7、事前登録の打ち切りの基準 = Opus で ②③ とも +5 未満）。

### 3-3.（ほぼ解消）E と A がどちらも音声の読みに触れる

E（音声の取りこぼし）は聞き取り・VAD・`audio/` を、A は `audio/recognizer.py` の読みの規則を触りうる。E が直しに入る
ときは verify-v1 を先に取り込み、`audio/recognizer.py` を触るなら A のセッションと順番を決める。E の調査は 10/19 の
記録で行い、測るときは推定器の版（内容の指紋）を書く。→ E の直しは verify-v1 に入った（`304a059`・`e850752`・`28f9b13`）。
A も同じ verify-v1 の上で `c299bb2` を入れたので、いまのところぶつかりは無い。

### 3-8.（解消）このブランチが verify-v1 の A の直しを持っていなかった

verify-v1 の `c299bb2`・`f4534a5`（A: ボードの札の確定 5 秒・片付けの束）はまだこのブランチに無い（E の直しは両方にある）。
B のオラクル・F の値の数え直しは、測る前に verify-v1 を取り込むか、比べる版を書く。G を verify-v1 へ入れるとき（オーナー）にも
先に取り込む。→ G を入れるときに取り込んだ。このブランチと verify-v1 は同じ中身。**A のセッションのブランチ
`claude/confident-hawking-5e4hff` は verify-v1 より遅れた**ので、A が次に push する前に verify-v1 を取り込む。

### 3-9. H と ADR-0063 D1・E・第 2 の耳

- ADR-0063 D1 は「推論は店舗 PC の CPU」。H3（ライブ）に進むなら新しい ADR で見直す。H1・H2 はオフラインなので決まりの範囲内。
- H2（営業のあとの書き起こし）は E の「聞き流した発話の書き起こし」（`tools/offplay_audio.py`）と同じ形。作るときは E の道具に
  クラウドの書き起こしを足す（別の道具を作らない）。
- Whisper を変えても第 2 の耳と短い語の分類器はそのまま。ただし推定器の読みの選択肢は Whisper の文から作るので、H を入れるときは
  物差し（`tools/bench_hands.py`）と 10/19 で測ってから。

### 3-10. I と B・E・第 2 の耳

- B の「ディーラーをセッションごとに記録できるか」は I2 の名乗りで答えが出る（ハンドごとのディーラーが記録に残る）。
- I は Whisper・第 2 の耳の読みを変えない（発話の重みの証拠を 1 つ足すだけ）。I3 で推定器に入れるときは B・F と同じく
  物差しと内容の指紋を記録して比べる。
- 話者のモデルは `models/speaker/`（約 28 MB）。I2 で店舗 PC に入れるときはインストーラの取得に足す（`models/` は更新で保持される）。

### 3-4. A が推定器の基準を動かし続ける

A のライブの規則は世界の再生にも効くので、直すたびに推定器の内容の指紋と物差し（開発データ 140/174・10/19 の数）が動く。
B・C は測るときの基準の版（内容の指紋・値の指紋・コミット）を記録し、比べるときは同じ版どうしで比べる。

### 3-5. B と E とこのセッションが同じブランチ

B・E・この台帳のセッションが `claude/project-plan-review-byn3lm` を使っている。push の前に必ず `git pull` する。
B が実装に入るとき（`integration/estimator.py` を大きく触る）は B 用に別のブランチを切る。
C の道具は 10/24 に消した（オーナー）。推定器の `HandWindow.seeds` を消したので**このブランチの推定器の内容の指紋は変わった**（推定の結果は同じ = seeds は既定で空だった）。B のオラクルの実行中の数字は消す前の版のもの。

### 3-6. F と B が同じ対応づけを要る

F（値を数える）の最初の段（F1 = 真の列と観測の対応づけの道具）と、B の ① 任意の列の採点は、どちらも「真のアクションの
行を発話・札の離脱に対応づける」部品が要る。先に作った側がそれを台帳に書き、もう片方は作らずに使う。F が
`integration/estimator.py` の値を変えるときは B・A と同じファイルなので、変える前に verify-v1 を取り込む。

### 3-7. G と A がどちらもライブの経路を触る

G は `main.py`（起動の設定）・`integration/engine.py`（時計・`set_level`）・`core/poker_engine.py`（アンテ）を変えた。A が同じ
ファイルを触っているので、G を verify-v1 に入れる前に verify-v1 を取り込む（このブランチで済ませている）。G の変更は既定
（リングゲーム・アンテなし）で記録を変えないので、推定器の物差しの数は動かない（内容の指紋は動く）。

## 4. 進める順（推す案）

1. ~~A の計画を承認する~~ → 済み・push 済み。**店舗 PC で `update.cmd`**（A のボードの規則・E の聞き取りの直しと書き起こしの自動化・G の卓の設定画面が入る。ロガーを起動すると PC のブラウザに設定の画面が開く）。
2. B のオラクルの結果を待つ（実行中）。「表せない」の中で真のベット / レイズの発話がどこにも無いハンドの数が、E の直しの効き目の目安になる。
3. 次の店舗テストのあと: E の書き起こし（`off_*.wav`）が店舗 PC で動くか・10/19 と同じ数え方で取りこぼしが減ったかを見る。
4. 2 と 3 の結果を並べて、v2 に進むか（② 以降）・F をいつ始めるか・11 月初めの判断（§3-1）をオーナーが決める。
5. ~~G を verify-v1 に入れる~~ → 済み（オーナー 10/24）。
