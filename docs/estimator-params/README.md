## 1. 目的

推定器 v1 の採点（`integration/estimator.py:SessionEstimator.score()`）は log 確率の足し算で、値（`PARAMS` と
`tools/estimate.py` の読みの値）の多くは**手で置いた**か、**4 席・プレイヤーなしの卓の小さな数**（5/11・0/14・2/80 など）
から置いた。10/19 の 8 人卓・プレイヤーありのテストでは推定の全部正しいハンドが 20/109 で、監査 4 回目は値が卓の種類で
外れていることを示した（例: 声のフォールド ÷ 真のフォールド = 開発データ 1.35 / d01277f8 0.72）。

F の目的は、**真のアクションのあるハンドで、採点の各項が数えている出来事を実際に数え、今の値と並べる**こと。
数えた値・区間・卓の種類ごとの違いを 1 つの表にし、どの値が正解を嫌っているかを分かるようにする。

## 2. やること・やらないこと

- やる:
  - 真のアクションと観測（発話・札の在否・ボードの時刻）を対応づける道具（§4）。
  - 採点の項ごとの数え上げ（§3 の表）と、卓の人数・セッション・プレイヤーの有無ごとの層別。
  - 結果の表（`docs/estimator-params/measured.md`）と機械で読める出力（`docs/estimator-params/measured.json`）。
  - 値を差し替えたときの物差しの感度（`tools/sweep_estimator.py`）。
  - 値を変える提案（推定器の値を実際に変えるのは §6 の手順を通したときだけ）。
- やらない:
  - ライブの経路（`integration/engine.py` の規則）・店舗 PC・音声の読み取りの変更。
  - 推定器の探索や項の形の変更（形を変えるのは B）。F は**今の項の値**を数える。
  - 真のアクションの修正（食い違いを見つけたら作業ログに書き、オーナーに確かめる）。

数え方の決まり:

- 割合は **数えた数 / 母数** と **Jeffreys の区間**（または Wilson の 95% 区間）を必ず並べる。母数 20 未満は「目安」と書く。
- 時刻の分布は最尤で当てはめ、ブートストラップの 90% 区間を付ける（今の `fold_lag_b_late` の決め方と同じ）。
- **層別**: 卓の人数（2〜4 / 5〜6 / 7〜8）・セッション・プレイヤーの有無（1 人で何席も打つ練習 / プレイヤーあり）・
  ディーラー（記録があれば）。セッションごとの割合は全体へ縮めた値（ベータ・二項の経験ベイズ）も出す。
- 真のアクションの「自信なし」の行・評価から外したハンドは数えない（物差しの `truth_exclusions` と同じ）。
  記録を見たあとに直した行（`lint_confirmed` など）の有無で分けて、結果が変わるかも見る。

## 4. 対応づけの道具（最初に作る）

`tools/count_penalties.py`（新規。推定器から import しない = 内容の指紋に入らない）:

1. 入力: 物差しと同じセッション（`tools/bench_hands.py:v1_inputs` → `tools/estimate.py:SessionInput`）と、
   ハンドの窓（`integration/estimator.py:SessionEstimator.windows()`）。真のアクションは `expected.json` の `truth`。
2. 発話: 窓の中の書き起こしをいまの読み取りで読む（`integration/world_replay.py:read_utterance`）。読みの選択肢は
   `tools/estimate.py:utterance_options`（第 2 の耳の候補・決まり文句の下のアクションなど、logp つき）。
3. **真の行と語の単調な対応づけ**（動的計画法）: 真の行は「語と組む / 言われない」、語は「行と組む / 余計な語」。
   組める条件 = 種類が同じ（オールインは同額の call / bet / raise と同じ = `tools/measure_capture_accuracy.py:same_action_type`）
   かつ時刻がそのストリートの札のあと。発話ごとに読みを 1 つ選ぶ（数えるときは「最も多くの真の行を説明する読み」を選び、
   どの読みで説明したかも残す = 読みの値の当たりの割合に使う）。
4. 札の離脱: 真のフォールドごとにその席の離脱を組み、残った離脱を「ショーダウン・片付け」「持ち上げ」に分ける
   （`integration/world_replay.py:PresenceTimeline.departures`、今の `_departure_terms` と同じ窓・同じ `blip_sec` / `flicker_sec`）。
5. 出力: ハンドごとの対応づけ（真の行 → 発話・読み・離脱）を JSON に（`--dump`）。見直しの画面（`tools/estimate_review.py`）で
   開けると、対応づけの誤りを人が確かめやすい（任意）。

**B との分担**: 台帳の B の最初の段（① 任意の列の採点 = オラクルの採点）も同じ「真の列と観測の対応づけ」を要る。
どちらかが先に作ったら、もう片方はそれを使う（同じものを 2 つ作らない）。先に作った側が台帳に書く。

**注意**: 対応づけそのものが値に依存しないようにする（今の推定器の点では選ばない）。ずれやすい所（同じ種類の語が続く・
語が離れて言われる）は 1 ハンドずつ目で確かめ、確かめたハンドの割合を報告する。

## 6. 値を変えるときの手順（推定器に入れる場合）

1. 変える値と根拠（数えた値・区間・層）を作業ログに書いてから変える。1 回に変える値は少数にし、変えた理由ごとに分ける。
2. `TZ=Asia/Tokyo python tools/bench_hands.py --twice --search-check --workers 3`: 前の記録（`tests/fixtures/store/bench_record.json`）と
   比べて**新しい要確認なしの誤り 0**（終了コード 1 なら入れない）。悪くなったハンドは名前を全部出す。
3. `TZ=Asia/Tokyo python tools/compare_versions.py <前のコミット>`: ハンドごとの正誤の変化。
4. 開発データは**標本内**（値を数えたデータで測る）なので、数字は「悪くならない」の見張りにしか使わない。精度は
   前向きの成績表（`tools/forward_ledger.py`）と、次の新しいセッションで見る（`docs/estimator.md` §8）。
5. `docs/estimator.md` §3.3 の表と §6 の変更の表を直す。値の指紋（`params_hash`）・内容の指紋（`content_hash`）を記録する。
6. 推定器の値を変えるのは B・台帳の A と同じファイル（`integration/estimator.py`）に触るので、変える前に `verify-v1` の最新を取り込む。
